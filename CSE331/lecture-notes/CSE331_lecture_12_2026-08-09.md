# CSE331 — Lecture 12: Context-Free Grammars — Definition, Derivations, Parse Trees, Ambiguity

This starts a new unit — Context-Free Languages — directly following Lecture 11's Pumping Lemma / non-regularity content for regular languages. Corresponds to Topics 10–11 in `cse331_topics.md`.

## Context-Free Grammars (CFG) — Definition

**Regular languages are a strict subset of context-free languages:**

$$RL \subsetneq CFL$$

## Formal Definition

A CFG is a 4-tuple $(V, \Sigma, R, S)$:

- $V$ — **Variables** (non-terminal symbols)
- $\Sigma$ — **Terminating symbols** (terminals) — e.g. $\{a, b, \varepsilon\}$
- $R$ — **Production rules**
- $S$ — **Starting symbol**

## Example Grammar

$$S \to AB$$
$$A \to Aa \mid \varepsilon$$
$$B \to Bb \mid \varepsilon$$

$A$ generates any number of $a$'s (including zero), $B$ generates any number of $b$'s (including zero) — independently of each other. So this grammar generates:

$$L = \{a^n b^m \mid n, m \geq 0\}$$

## Derivations — Leftmost vs. Rightmost

> [!info] Note from the board
> The very first step, $S \to AB$, is trivially **both** leftmost and rightmost at once — $S$ is the only variable present, so there's no choice of which variable to expand yet. The leftmost/rightmost distinction only becomes meaningful from the second step onward, once there are multiple variables in the string to choose between.

### Leftmost derivation (example: producing $a^2b^2 = aabb$)

At each step, expand the **leftmost** variable in the string first.

$$S \to AB \to AaB \to AaaB \to aaB \to aaBb \to aaBbb \to aabb$$

Step-by-step:
1. $S \to AB$
2. $A \to Aa$: $AB \to AaB$
3. $A \to Aa$: $AaB \to AaaB$
4. $A \to \varepsilon$: $AaaB \to aaB$
5. $B \to Bb$: $aaB \to aaBb$
6. $B \to Bb$: $aaBb \to aaBbb$
7. $B \to \varepsilon$: $aaBbb \to aabb$

### Rightmost derivation (same target string $aabb$)

At each step, expand the **rightmost** variable in the string first.

$$S \to AB \to ABb \to ABbb \to Abb \to Aabb \to Aaabb \to aabb$$

Step-by-step:
1. $S \to AB$
2. $B \to Bb$: $AB \to ABb$
3. $B \to Bb$: $ABb \to ABbb$
4. $B \to \varepsilon$: $ABbb \to Abb$
5. $A \to Aa$: $Abb \to Aabb$
6. $A \to Aa$: $Aabb \to Aaabb$
7. $A \to \varepsilon$: $Aaabb \to aabb$

Both derivations produce the same terminal string, $aabb$.

## Parse Trees

> [!important] From the board: $\varepsilon$ must be written explicitly in the parse tree, even though it contributes no symbol to the final string — it represents the production that terminated that branch.

**Key point from class:** the leftmost and rightmost derivations of the same string produce the **same parse tree** — derivation order is just a convention for which variable to expand next; it doesn't change the tree's shape. (One earlier attempted tree on the board was crossed out and redrawn — not reproduced here.)

Parse tree for $S \Rightarrow^* aabb$ (both derivations above):

```
                S
             /     \
            A       B
          /   \   /   \
         A     a B     b
       /   \      /  \
      A     a    B    b
      |          |
      ε          ε
```

Reading the leaves left to right: $\varepsilon, a, a$ (from the $A$ subtree) then $\varepsilon, b, b$ (from the $B$ subtree) $\to aabb$.

## Ambiguous Grammars

A grammar is **ambiguous** if some string in its language has more than one parse tree (equivalently, more than one leftmost derivation).

### Example grammar

$$E \to E + E \mid E \times E \mid a$$

### Witness string: $a + a \times a$

**Leftmost derivation 1** — expand the $+$ first:

$$E \to E+E \to a+E \to a+E \times E \to a+a \times E \to a+a \times a$$

This reads as $a + (a \times a)$.

**Leftmost derivation 2** — expand the $\times$ first:

$$E \to E \times E \to E+E \times E \to a+E \times E \to a+a \times E \to a+a \times a$$

This reads as $(a + a) \times a$.

Both derivations are leftmost, both are valid under the grammar, and both produce the exact same terminal string $a+a\times a$ — but they group the operators differently, giving two distinct parse trees:

**Tree 1** — $a + (a \times a)$:
```
        E
      / | \
     E  +  E
     |    / | \
     a   E  ×  E
         |     |
         a     a
```

**Tree 2** — $(a + a) \times a$:
```
        E
      / | \
     E  ×  E
   / | \    |
  E  +  E   a
  |     |
  a     a
```

Two distinct parse trees for one string $\Rightarrow$ the grammar $E \to E+E \mid E\times E \mid a$ is **ambiguous**.

## New Example Started (cut off — continues next lecture)

$$S \to (S) \mid SS \mid \varepsilon$$

Only these three lines were written before the page ends. This is the **balanced (well-matched) parentheses language** — every `(` has a matching `)`, properly nested, nothing left dangling.

**Context from the board:** TNF connected this to checking whether a bracket is **opened but never closed** — the motivation for the next topic, Pushdown Automata (Topic 13):

- A DFA (finite states = bounded memory) cannot recognize this language in general, because checking bracket-matching requires *counting* how many brackets are currently open, and that count is unbounded under arbitrary nesting depth. This is provable by the Pumping Lemma the same way $\{0^n1^n\}$ was shown non-regular in Lecture 11 — $\{(^n)^n\}$ is structurally identical.
- This is exactly why CFGs need a **stack** (a Pushdown Automaton) to be recognized computationally: push on every `(`, pop on every `)`. A string is valid iff the stack is empty at the end. Empty stack + closing bracket $\to$ closed without an open. Non-empty stack at the end $\to$ **opened but never closed**.
- This stack algorithm is the real-world version of the same idea — it's how compilers, editors, and parsers (e.g. JSON validators) flag unclosed/mismatched bracket errors.
