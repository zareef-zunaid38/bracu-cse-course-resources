📖 Theory ▼
SELECT clause execution order HIGH

A query is written SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY, but the database executes it in a different order:

1
FROM — specify tables
2
WHERE — filter rows/records
3
GROUP BY — group filtered rows/records
4
HAVING — filter groups
5
SELECT — select columns and expressions
6
ORDER BY — sort the result
7
LIMIT/OFFSET — limit the number of returned rows

Direct from the lecture slide (faculty's own example):

SELECT major, AVG(cgpa) AS avg_cgpa FROM Lab_Grades
WHERE days_present > 10
GROUP BY major
HAVING AVG(cgpa) > 3.5
ORDER BY avg_cgpa DESC
LIMIT 1;
Why it matters: FROM runs first, then WHERE filters, then the filtered rows are GROUP'ed BY major, then HAVING filters the grouped rows, then the result is SELECT'ed, then ORDER'ed BY avg_cgpa descending, then LIMIT'ed to the first row. This exact walk-through phrasing is the faculty's own explanation — expect a question that asks you to narrate execution order like this.
Aggregate vs. scalar functions HIGH

Aggregate functions operate on multiple values and return one output from many: AVG(), COUNT(), MAX(), MIN(), SUM(), STD(), VARIANCE().

Scalar functions operate on a single value and return one output per value: UPPER(), LOWER(), ROUND(), REVERSE(), LENGTH().

Common error: Confusing which category a function belongs to changes what you expect the output shape to be — an aggregate collapses your rows, a scalar doesn't.
GROUP BY HIGH

Groups rows sharing the same value; mostly used with aggregate functions but also valid without one (e.g. as a dedup-style listing).

SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades GROUP BY major;
-- CS: 3.57–4.00 | CSE: 3.70–3.86 | ECE: 3.25–3.67

SELECT major FROM Lab_Grades GROUP BY major;
-- lists each distinct major once, same effect as SELECT DISTINCT major
Common error: Grouping by a column with the wrong granularity silently changes the meaning of the result. Grouping by major gives one row per major; grouping by submission_date instead gives one row per distinct date — a different breakdown, not a refinement.
HAVING vs WHERE HIGH

WHERE filters rows before grouping happens; used before grouping. HAVING filters groups after aggregation; used afterwards, and mostly used with aggregate functions.

SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades
GROUP BY major HAVING COUNT(*) >= 3;
-- only CS qualifies (3 students); CSE and ECE (2 each) are dropped

SELECT name, cgpa FROM Lab_Grades HAVING cgpa > 3.7;
-- HAVING can filter without GROUP BY too — behaves like a post-SELECT WHERE

SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades
WHERE submission_date <= '2018-09-15' GROUP BY major;
-- WHERE removes rows first (submitted after 9/15 excluded), THEN grouping runs
-- on what's left — CS's range changes from 3.57-4.00 to 3.91-4.00
Key insight: The third example shows WHERE and GROUP BY chained — WHERE's row-level filter happens first and can change which rows are even available to be grouped, which changes the per-group MIN/MAX.
Subqueries / nested queries HIGH

A query inside another query. The inner query executes first; its result (single value or multiple values) is used by the outer query. Per the faculty's own slide, a subquery can be placed after WHERE, FROM, SELECT, or HAVING — not just WHERE. Know all four placements:

-- WHERE
SELECT name FROM Lab_Grades
WHERE project_marks = (SELECT MAX(project_marks) FROM Lab_Grades);

-- FROM (a subquery standing in as a table)
SELECT AVG(cgpa) FROM
  (SELECT cgpa FROM Lab_Grades WHERE major = 'CSE') AS CSE_CGPAs;

-- SELECT (a subquery as a computed column)
SELECT name, (SELECT MAX(cgpa) FROM Lab_Grades) AS MAX_UNIVERSITY_CGPA
FROM Lab_Grades;

-- HAVING
SELECT major, AVG(cgpa) AS avg_cgpa FROM Lab_Grades
GROUP BY major
HAVING AVG(cgpa) > (SELECT AVG(cgpa) FROM Lab_Grades);
Common error: "Retrieve the name of the student with the highest marks" via WHERE project_marks = (SELECT MAX(project_marks) ...) only returns one row if the max is unique. With ties (as in this dataset — Nafis and Arafat both have 20), it correctly returns both.
ANY / ALL HIGH

> ANY (subquery) is true if the comparison holds for at least one value in the subquery's result (equivalent to comparing against the minimum). > ALL (subquery) is true only if it holds for every value (equivalent to comparing against the maximum). A logical operator (=, <, >, <=, >=, <>) always precedes ANY/ALL.

Important — this is not a correlated subquery: the faculty's own ANY/ALL example compares one fixed group against another fixed group. It does not need a self-alias, because the outer row and the subquery aren't the same table reference.
-- ANY: is any CSE student's cgpa higher than any CS student's?
SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ANY (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');
-- returns Nafis (3.86) and Tasneem (3.7) — both beat at least one CS cgpa

-- ALL: is a CSE student's cgpa higher than every CS student's?
SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ALL (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');
-- returns an empty set — no CSE student beats all three CS cgpas (3.91, 3.57, 4.0)
Correlated subqueries (self-alias) HIGH

A subquery that references a column from the outer row, so it re-evaluates once per outer row instead of once total. When both queries hit the same table, alias it twice (L1, L2) so the engine treats them as separate instances. This is where the faculty's real examples use ANY/EXISTS correlated to the outer row — unlike the plain ANY/ALL example above.

Faculty example — majors with at least one low performer (correlated EXISTS):

SELECT DISTINCT major FROM Lab_Grades L1
WHERE EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.major = L1.major AND L2.cgpa < 3.7
);
-- returns CS and ECE (each has a student below 3.7 cgpa); CSE does not
EXISTS / NOT EXISTS HIGH

Returns TRUE if the correlated subquery returns at least one row — it only cares whether a match exists, not the actual values. NOT EXISTS is the faculty's preferred pattern for "find the maximum without using MAX()":

-- (b) highest project marks, via "nobody else beats me"
SELECT name FROM Lab_Grades L1
WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks > L1.project_marks
);
-- returns Nafis and Arafat (tied at 20 — neither is beaten by anyone)

-- (c) same idea, but require a UNIQUE maximum (note >= instead of >)
SELECT name FROM Lab_Grades L1
WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks >= L1.project_marks
);
-- returns an empty set — with >=, a tie counts as "someone else matches or beats me"
Key insight (this is the exact "what's the difference" question the lab sheet poses): Query (b) uses strict > — "no one scored strictly higher than me" — which tolerates ties, so both Nafis and Arafat pass. Query (c) uses >= — "no one scored higher than or equal to me" — which a tied student fails against their own duplicate value, so the result is empty when the max isn't unique.
Many ways to solve one task MED

The faculty explicitly teaches that "count students with the max marks" has at least three equivalent forms — recognizing the equivalence matters as much as producing one correct query:

-- 1. Correlated NOT EXISTS
SELECT COUNT(*) FROM Lab_Grades L1 WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks > L1.project_marks);

-- 2. Plain subquery with MAX()
SELECT COUNT(*) FROM Lab_Grades L1
WHERE project_marks = (SELECT MAX(project_marks) FROM Lab_Grades);

-- 3. Plain subquery with ALL
SELECT COUNT(*) FROM Lab_Grades L1
WHERE project_marks >= ALL (SELECT project_marks FROM Lab_Grades);

Bonus pattern — major with the most students enrolled (GROUP BY inside a subquery, compared with ALL):

SELECT major FROM Lab_Grades GROUP BY major
HAVING COUNT(*) >= ALL (SELECT COUNT(*) FROM Lab_Grades GROUP BY major);
DISTINCT MED

Removes duplicate rows from the result set. SELECT DISTINCT major lists each major once; without DISTINCT, a major appears once per matching row.

LIKE wildcards MED

% matches zero or more characters; _ matches exactly one character.

  • LIKE 'a%' — starts with "a"
  • LIKE '%a%a%' — contains at least two "a"s
  • LIKE 'a___' — starts with "a", exactly 4 characters total
ALTER TABLE variants LOW

ADD a new column, MODIFY COLUMN to change a column's data type, DROP COLUMN to remove one. Know the keyword differences — a common easy-marks question.

DROP TABLE / DATABASE LOW

Deletes the entire table or database structure, not just its rows. Irreversible without a backup — Lab 1 sheet explicitly warns not to try it during the session.

❓ Short Questions ▼

Tap a question to reveal the answer. Try to recall first.

What is the difference between WHERE and HAVING? HIGH
WHERE filters individual rows before any grouping occurs. HAVING filters groups after GROUP BY has aggregated them. Aggregate functions (COUNT, SUM, etc.) can only be used in HAVING, not WHERE, because they don't have a value until grouping has happened.
What does GROUP BY do, and what changes if you group by a different column? HIGH
GROUP BY clusters all rows sharing the same value in the grouped column(s) into one group per distinct value, so aggregate functions in SELECT compute per group. Grouping by a different column (e.g. submission_date instead of major) produces an entirely different breakdown — one row per distinct date rather than per major — not a variation of the same result.
What is the role of ANY and ALL in a subquery comparison — do they require a correlated subquery? HIGH
They compare a value against a whole set returned by a subquery. "> ANY (subquery)" is true if it's greater than at least one value in the set. "> ALL (subquery)" is true only if it's greater than every value in the set. No, they don't require correlation — the faculty's own example compares CSE students' cgpa against the fixed set of CS students' cgpa, a plain (non-correlated) subquery. Correlation is a separate, optional technique layered on top when the comparison set needs to change per outer row.
Why do correlated subqueries on the same table need two aliases (e.g. L1, L2)? HIGH
SQL needs to distinguish the outer query's current row from the inner subquery's row when both come from the identical table — otherwise a column reference like "major" is ambiguous as to which instance it belongs to. Aliasing the same table twice (L1 for outer, L2 for inner) creates two logically separate instances the engine can compare against each other.
In the "find max marks via NOT EXISTS" pattern, why does using > vs >= inside the subquery give different results? HIGH
With strict ">" ("no one scored strictly higher than me"), a tie is tolerated — both tied students pass, since neither is strictly beaten. With ">=" ("no one scored higher than or equal to me"), each tied student fails against the other's identical value, so if the maximum isn't unique, the query returns an empty set. This is the faculty's own worked distinction (Task 3, parts b and c) — expect it tested directly.
Where in a SELECT statement can a subquery be placed? MED
Four places: after WHERE (filtering rows against a computed value), after FROM (using the subquery's result as a derived table, must be aliased), after SELECT (as a computed scalar column), and after HAVING (filtering groups against a computed value).
Can HAVING be used without GROUP BY? MED
Yes — MySQL allows HAVING to filter rows post-SELECT even with no GROUP BY present, functioning similarly to a WHERE clause applied after the column list is computed (useful for filtering on a SELECT alias). It's non-standard-looking but is in the faculty's own slide example.
What's the difference between SELECT major and SELECT DISTINCT major? MED
SELECT major returns one row per matching record, so a major shared by several students appears repeatedly. SELECT DISTINCT major collapses those duplicates so each distinct major value appears exactly once.
What happens if UPDATE is run without a WHERE clause? MED
The SET clause applies to every row in the table, not just one — e.g. UPDATE Lab_Grades SET major='CSE'; would overwrite every student's major to CSE. WHERE is what scopes the update to specific rows.
What's the difference between ALTER ... ADD and ALTER ... MODIFY COLUMN? LOW
ADD introduces a brand-new column to the table. MODIFY COLUMN changes the definition (e.g. data type or size) of a column that already exists — it does not add or remove columns.
🧮 Query Practice ▼

All questions use the shared Lab_Grades schema: std_id, name, major, section, days_present, project_marks, cgpa, submission_date.

Q1 Retrieve the name and project marks of students majoring in CSE, sorted by marks descending. HIGH ▼
1
Select only the two needed columns: name, project_marks
2
Filter with WHERE major = 'CSE'
3
Sort with ORDER BY project_marks DESC
SELECT name, project_marks FROM Lab_Grades
WHERE major = 'CSE'
ORDER BY project_marks DESC;
Key insight: Straight WHERE + ORDER BY — this is the Lab 1 baseline every later query builds on.
Q2 Retrieve the name, days present, and marks of students whose marks are between 17 and 19 and who major in CS or CSE. HIGH ▼ 
SELECT name, days_present, project_marks FROM Lab_Grades
WHERE project_marks BETWEEN 17 AND 19
AND major IN ('CS', 'CSE');
Key insight: BETWEEN and IN are shorthand — the same query is expressible with >=/<= and OR/=, but the exam sheet explicitly asks you to recognize both forms.
Q3 List all student details sorted by name descending, then by submission date ascending. MED ▼ 
SELECT * FROM Lab_Grades
ORDER BY name DESC, submission_date ASC;
Key insight: Multi-column ORDER BY resolves ties in the first column using the second — e.g. the two students named "Tasneem" get ordered relative to each other by submission_date.
Q4 Retrieve the name(s) of the student(s) with the highest project marks, using a subquery. HIGH ▼
1
Inner query finds the max: SELECT MAX(project_marks) FROM Lab_Grades
2
Outer query matches rows equal to that value
SELECT name FROM Lab_Grades
WHERE project_marks = (SELECT MAX(project_marks) FROM Lab_Grades);
Exam note: This correctly returns every student tied for the max, not just one — with this dataset, Nafis and Arafat (both 20) both come back. If you only expected one row, that's the trap.
Q5 Find CSE students whose cgpa is higher than at least one CS student's, and separately, higher than every CS student's (ANY vs ALL, non-correlated). HIGH ▼ 
-- ANY
SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ANY (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');

-- ALL
SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ALL (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');
Exam note: No self-alias needed here — this is the faculty's actual example, and it is not correlated. ANY returns Nafis (3.86) and Tasneem (3.7), since each beats at least one of the CS cgpas (3.91, 3.57, 4.0). ALL returns an empty set, since no CSE cgpa beats all three.
Q6 Count students per major, showing only majors with at least 3 students (GROUP BY + HAVING). HIGH ▼ 
SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades
GROUP BY major
HAVING COUNT(*) >= 3;
Key insight: Trying WHERE COUNT(*) >= 3 here is the classic wrong answer — COUNT(*) doesn't exist until after grouping, so the filter has to be HAVING. With this dataset only CS (3 students) qualifies; CSE and ECE (2 each) are dropped.
Q7 Find the name(s) of the student(s) with the highest project marks, without using MAX() — using a correlated NOT EXISTS. HIGH ▼
1
Alias the table twice: L1 for "this student", L2 for "everyone else"
2
Exclude self with L2.std_id != L1.std_id
3
A student qualifies if NO other student (L2) has strictly higher marks
SELECT name FROM Lab_Grades L1
WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks > L1.project_marks
);
Key insight: This is logically identical to WHERE project_marks = (SELECT MAX(project_marks) FROM Lab_Grades) — the faculty's own slide shows three equivalent forms (NOT EXISTS, plain MAX subquery, and >= ALL) side by side specifically to test whether you recognize they're the same.

SQL — Database and table setup (Lab 1)
CREATE DATABASE DB_Name;
USE DB_Name;

CREATE TABLE Lab_Grades (
    std_id char(4),
    name varchar(30),
    major char(3),
    section char(1),
    days_present int,
    project_marks double,
    cgpa decimal(3,2),
    submission_date date
);

DESCRIBE Lab_Grades;
SHOW TABLES;
Know DESCRIBE (shows structure/column types) vs SHOW TABLES (lists tables in the current database) — easy to confuse under time pressure.
SQL — Insert, alter, update, delete (Lab 1)
INSERT INTO Lab_Grades VALUES
('s001','Abir','CS','1',10,18.5,3.91,'2018-09-15');

ALTER TABLE Lab_Grades ADD project_title char(10);
ALTER TABLE Lab_Grades MODIFY COLUMN project_title varchar(50);
ALTER TABLE Lab_Grades DROP COLUMN project_title;

UPDATE Lab_Grades SET major = 'CSE' WHERE name = 'Arafat';
DELETE FROM Lab_Grades WHERE name = 'Naima';
DELETE FROM Lab_Grades WHERE days_present < 8;
DELETE without WHERE removes every row; DROP TABLE/DATABASE removes the structure itself. Both UPDATE and DELETE are scoped entirely by their WHERE clause.
SQL — SELECT variations (Lab 1)
SELECT name, project_marks+days_present*5/12 AS total_marks
FROM Lab_Grades;

SELECT UPPER(name), LOWER(name) FROM Lab_Grades;
SELECT DISTINCT major FROM Lab_Grades;

SELECT * FROM Lab_Grades WHERE name LIKE 'a%';
SELECT * FROM Lab_Grades WHERE name LIKE '%a%a%';
SELECT * FROM Lab_Grades WHERE name LIKE 'a___';
AS creates a computed column alias. LIKE wildcards: % = any length, _ = exactly one character.
SQL — Aggregate functions individually (Lab 2, Task 1)
SELECT MIN(cgpa) FROM Lab_Grades;                              -- 3.25
SELECT COUNT(*) AS total_students, AVG(project_marks) AS average_marks
  FROM Lab_Grades;                                              -- 7, 18.5
SELECT SUM(days_present) FROM Lab_Grades;                       -- 70
SELECT MAX(submission_date) AS last_submission FROM Lab_Grades; -- 2018-09-18
Each returns one output collapsed from all 7 rows — the defining trait of an aggregate function.
SQL — GROUP BY and HAVING (Lab 2, Task 1)
SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades GROUP BY major;
SELECT major, COUNT(*) FROM Lab_Grades GROUP BY major;
SELECT major, MIN(cgpa), MAX(cgpa) FROM Lab_Grades
  GROUP BY major HAVING COUNT(*) >= 3;        -- only CS survives
SELECT name, cgpa FROM Lab_Grades HAVING cgpa > 3.7;  -- HAVING with no GROUP BY
Every non-aggregated column in SELECT should appear in GROUP BY, or the result is ambiguous. Note the last line — HAVING doesn't strictly require GROUP BY in MySQL.
SQL — Subqueries in all four clause positions (Lab 2, Task 2)
-- WHERE
SELECT name FROM Lab_Grades
WHERE project_marks = (SELECT MAX(project_marks) FROM Lab_Grades);

-- FROM (derived table, must be aliased)
SELECT AVG(cgpa) FROM
  (SELECT cgpa FROM Lab_Grades WHERE major = 'CSE') AS CSE_CGPAs;

-- SELECT (scalar subquery as a computed column)
SELECT name, (SELECT MAX(cgpa) FROM Lab_Grades) AS MAX_UNIVERSITY_CGPA
FROM Lab_Grades;

-- HAVING
SELECT major, AVG(cgpa) AS avg_cgpa FROM Lab_Grades
GROUP BY major
HAVING AVG(cgpa) > (SELECT AVG(cgpa) FROM Lab_Grades);
Four placements taught explicitly by the faculty — expect a question that specifically tests recognizing an unfamiliar placement (FROM or SELECT), not just the common WHERE case.
SQL — ANY / ALL, non-correlated (Lab 2, Task 2)
SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ANY (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');

SELECT * FROM Lab_Grades WHERE major = 'CSE'
AND cgpa > ALL (SELECT cgpa FROM Lab_Grades WHERE major = 'CS');
No self-alias here — both major filters are independent, so this is a plain subquery, not correlated.
SQL — Correlated subqueries, EXISTS / NOT EXISTS (Lab 2, Task 3)
-- (a) majors with at least one student below 3.7 cgpa
SELECT DISTINCT major FROM Lab_Grades L1
WHERE EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.major = L1.major AND L2.cgpa < 3.7
);

-- (b) highest project marks (ties tolerated)
SELECT name FROM Lab_Grades L1
WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks > L1.project_marks
);

-- (c) highest project marks, UNIQUE only (note >=)
SELECT name FROM Lab_Grades L1
WHERE NOT EXISTS (
  SELECT * FROM Lab_Grades L2
  WHERE L2.std_id != L1.std_id AND L2.project_marks >= L1.project_marks
);
(b) returns Nafis and Arafat (tied at 20). (c) returns an empty set — with >=, each tied student is "matched" by the other's equal value, so neither passes.

🧠 Mnemonics & Memory Aids ▼
"Fresh Waffles Get Half Servings, Limited"
Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT/OFFSET.
"Rows first, groups second"
WHERE = row-level filter (runs early). HAVING = group-level filter (runs after GROUP BY). If the condition needs an aggregate function, it belongs in HAVING.
"One table, two hats"
Correlated subquery on the same table needs two aliases (L1/L2) — think of it as the same table wearing a different hat in the inner query. But ANY/ALL alone doesn't need this — only add hats when the outer row's own value feeds into the inner query's filter.
"Strict beats ties, or-equal breaks them"
In a "no one beats me" NOT EXISTS query: > lets tied students both win; >= makes every tied student lose to the other's identical value.
