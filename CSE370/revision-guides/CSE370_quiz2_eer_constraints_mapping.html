📖 Theory ▼
Specialization & Generalization HIGH

Specialization is the process of defining a set of subclasses of a superclass, based on some distinguishing characteristic (e.g. Student → Undergrad, Graduate, by degree level). Generalization is the reverse: several entity types with common attributes are generalized into a superclass, and the originals become its subclasses (e.g. TheoryRoom + LabRoom → Classroom).

The subclass/superclass relationship is also called an IS-A relationship (an Undergrad IS-A Student). A subclass inherits all attributes and relationships of its superclass, plus it may define its own local attributes/relationships. A superclass can have several independent specializations at once (e.g. Faculty specializes both by contract type {Contractual, Full-time} and by rank {Lecturer, Assistant Prof, ...}).

Common error: given an EER diagram, you often cannot tell whether it was built via specialization or generalization — both produce the same diagram. Don't assume the direction from the picture alone.
Constraints on Specialization/Generalization HIGH

Two independent constraint types apply to every specialization:

  • Disjointness constraint (max membership) — d = disjoint: an entity belongs to at most 1 subclass in that specialization (e.g. a Vehicle is Car or Truck or Bus, never two). o = overlapping: an entity may belong to more than one subclass at once (e.g. a Student can be both StudentTutor and ResearchAssistant).
  • Completeness constraint (min membership) — Total (double line): every superclass entity must belong to at least 1 subclass (e.g. every Student is Undergrad or Graduate). Partial (single line): an entity may belong to none of the subclasses (e.g. not every Student is a StudentTutor or ResearchAssistant).

These combine into 4 possibilities: disjoint-total, disjoint-partial, overlapping-total, overlapping-partial.

Why it matters: the disjoint/overlapping + total/partial combination is exactly what determines which Step-8 mapping option (8A–8D) is valid — see Theory block below and the EER Mapping Options analytical question.
Relational Integrity Constraints (the 4) HIGH

Conditions that must hold on every valid relation state, preventing invalid data:

  • Domain constraint — every value in a tuple must come from its attribute's domain (data type + optional range/format), or be null if allowed. E.g. Age must be a positive integer < 100.
  • Key constraint — every value for a key must be unique across all tuples in the relation (no two rows share the same primary/candidate key value).
  • Entity Integrity constraint — primary key attributes of a relation cannot be null in any tuple. If the PK is composite, none of its component attributes may be null. (Non-key attributes can still be separately constrained NOT NULL, but that's a different rule.)
  • Referential Integrity constraint — a foreign key value must either (1) match an existing primary key value in the referenced table, or (2) be null — but only if that FK is not itself part of the referencing table's primary key.
Common error: Entity Integrity only bans nulls in the primary key, not in every attribute — don't overgeneralize it.
Superkey, Key, Candidate Key, Primary Key, Foreign Key MED

Superkey — any attribute (or set) that has a unique value for every tuple. Key — a minimal superkey: removing any attribute from it destroys uniqueness. A relation can have several keys, all called candidate keys; one is chosen as the primary key (standard practice: smallest/simplest candidate). Foreign key — an attribute (or set) in one relation that references the primary key of another (or the same, for recursive) relation.

  • Example: in Student(ID, Name, Email), both {ID} and {Email} are candidate keys; {ID, Name} is a superkey but not a key (Name is not needed for uniqueness).
ER → Relational Mapping: Steps 1–7 HIGH

Standard 7-step algorithm to turn an ER diagram into relational tables:

  1. Regular entity types — one table each; simple attributes become columns, composite attributes contribute their simple components as columns, multivalued and derived attributes are skipped here.
  2. Weak entity types — one table each; add the owner's PK as a foreign key; the combined (owner FK + partial key) becomes the weak entity's PK.
  3. Binary N:M relationships — a new table (cross-referencing approach); add both sides' PKs as FKs, combined = new PK; add any relationship attributes here.
  4. Binary 1:N relationships — foreign-key approach (preferred over cross-referencing — more space efficient): add the "1" side's PK as an FK on the "N" side's table; relationship attributes also go on the "N" side.
  5. Binary 1:1 relationships — 3 options: cross-referencing (as step 3), merged relation (combine into one table — can waste space), or foreign key (add either side's PK as FK to the other — put it on the side with total participation to avoid nulls).
  6. Multivalued attributes — separate table per multivalued attribute; owner's PK as FK + the value itself (both underlined as combined PK). For multivalued-composite attributes, add only the simple components as separate columns.
  7. N-ary relationships — one table; PKs of all connected entities become FKs, combined as PK; plus any relationship attributes.

Recursive relationships map the same way based on their cardinality (N:M → cross-referencing, 1:N → FK approach, 1:1 → either).

EER → Relational Mapping: Step 8 (Specialization/Generalization) HIGH

Four options exist for mapping a specialization/generalization to tables:

OptionStructureApplies when
8ASeparate table for superclass + each subclass. Superclass PK is FK (and PK) in every subclass table.Always valid — the general-purpose default.
8BTable only for each subclass (no superclass table); superclass attributes duplicated into each.Only if total — every superclass member belongs to some subclass. (If partial, non-member data is lost.)
8CSingle merged table + one "type" attribute as discriminator.Only if disjoint — one type flag can't represent overlapping membership.
8DSingle merged table + N boolean flag attributes (one per subclass).Works for any case, but wastes space for disjoint specializations (only 1 flag is ever true).
Why it matters: the lecture's worked PERSON→EMPLOYEE/ALUMNUS/STUDENT example uses 8A for the top level but folds STUDENT_ASSISTANT's disjoint sub-specialization (Research/Teaching Assistant) into flags (Ra_flag, Ta_flag) inside the EMPLOYEE table — a mixed real-world design, not a pure textbook case.
Enforcing Constraints via SQL (ON DELETE / ON UPDATE) MED

Constraint enforcement in DDL: PRIMARY KEY + NOT NULL stop entity-integrity violations; UNIQUE stops key-constraint violations on non-PK candidate keys; data type + CHECK stop domain violations; FOREIGN KEY ... REFERENCES stops referential-integrity violations on insert.

For DELETE/UPDATE on a referenced row, the FK declaration's ON DELETE / ON UPDATE clause picks one of 3 behaviors: Restrict (block the operation), Cascade (propagate the delete/update to referencing rows), Set Null (null out the FK — only legal if that FK is not part of the referencing table's own PK).

❓ Short Questions ▼

Tap a question to reveal the answer. Try to recall first.

What is the difference between specialization and generalization? HIGH
Specialization starts from a superclass and defines subclasses based on a distinguishing characteristic (top-down). Generalization starts from several entity types with shared attributes and merges them into one superclass, with the originals becoming subclasses (bottom-up). Given only the final EER diagram, you generally cannot tell which process produced it.
What do the symbols 'd' and 'o' mean on an EER diagram, and how is that different from single vs. double lines? HIGH
'd' and 'o' encode the disjointness constraint: d = disjoint (entity belongs to at most one subclass), o = overlapping (can belong to more than one). Single vs. double connecting lines encode a completely separate constraint, completeness: single = partial (an entity may belong to none of the subclasses), double = total (every entity must belong to at least one). The two constraints combine independently — e.g. "overlapping-partial" is a valid combination.
Under what condition can a foreign key column contain NULL? MED
Only if that foreign key attribute is not part of the referencing table's own primary key. If it is part of the PK, the Entity Integrity constraint forbids null regardless of what Referential Integrity would otherwise allow.
What's the difference between a superkey and a key (candidate key)? MED
A superkey is any attribute set that uniquely identifies each tuple — it may contain redundant attributes. A key is a minimal superkey: every attribute in it is necessary for uniqueness, so removing any one of them breaks uniqueness. Every key is a superkey, but not every superkey is a key.
Why is the foreign-key approach preferred over cross-referencing for 1:N relationships? MED
Cross-referencing (making a separate relationship table) works for 1:N but is inefficient — it duplicates the "1" side's key once per related row unnecessarily. The foreign-key approach instead adds a single FK column directly on the "N" side's table, avoiding the extra table and redundant storage.
When mapping a weak entity type, what makes up its primary key in the relational schema? MED
The combination of the owner entity's primary key (added as a foreign key) plus the weak entity's own partial key. Both are underlined together as the combined primary key of the weak entity's table.
List the four EER-to-relational mapping options (8A–8D) and when each is valid. HIGH
8A: separate table for superclass + each subclass (always valid). 8B: tables only for subclasses, no superclass table (valid only if total — otherwise non-member data is lost). 8C: one merged table with a single type/discriminator attribute (valid only if disjoint). 8D: one merged table with N boolean flag attributes, one per subclass (valid for any case, but wastes space when disjoint).
Which constraints can each of INSERT, DELETE, and UPDATE violate? MED
INSERT can violate any of the 4 (domain, key, entity integrity, referential integrity). DELETE can only violate referential integrity (deleting a row whose PK is still referenced elsewhere). UPDATE's exposure depends on which attribute is touched: domain constraint always possible; key/entity integrity if a key attribute is updated; referential integrity if a foreign key value or a referenced primary key value is updated.
In a 1:1 relationship mapped via the foreign key approach, which side should get the FK? LOW
Put the foreign key on the entity table that has total participation in the relationship. That guarantees the FK column is never null on that side, avoiding wasted/unnecessary null values.

Q3 Student(ID, Name, CGPA) "joins" Program(PID, Name, totalCredits) — a 1:N relationship (many Students, one Program), with relationship attribute completeCredit. Map using the foreign key approach. MED ▼
1
Identify the "1" side (Program) and the "N" side (Student) of the relationship.
2
Add Program's PK as a foreign key on the Student table (the "N" side), not the other way around.
3
Add the relationship attribute (completeCredit) to the same "N"-side table.

Result: Program(PID, Name, totalCredits). Student(ID, Name, CGPA, PID, completeCredit) — PID is FK→Program.

Key insight: for 1:N, the FK always goes on the "many" side — putting it on the "1" side would require a multivalued column, which relational tables cannot hold directly.

∑ Mathematics ▼
Superkey (formal condition)
K is a superkey of R ⇔ ∀ t1, t2 ∈ r(R), t1 ≠ t2 ⟹ t1[K] ≠ t2[K]
Where: r(R) = the current set of tuples (rows) in relation R; t1[K] = the projection of tuple t1 onto attribute set K.
Key (minimal superkey)
K is a key of R ⇔ K is a superkey AND ∀ A ∈ K, (K − {A}) is NOT a superkey
Where: A is any single attribute in K. The second line is the minimality test — every attribute must be pulling its weight.
Ex Given Student(ID, Name, Email, Phone) where ID and Email are each individually unique, classify {ID}, {ID, Name}, and {Email, Phone}. HIGH ▼
1
{ID}: unique on its own, and it's a single attribute so it's trivially minimal → it is a key (candidate key).
2
{ID, Name}: unique (since ID alone is unique), but removing Name still leaves {ID} unique → Name is redundant → this is a superkey but not a key.
3
{Email, Phone}: Email alone is already unique, so {Email, Phone} is unique too, but Phone is redundant for uniqueness → also a superkey but not a key (the key here is really just {Email}).
Pattern: any superset of a key is automatically a superkey but never a key (minimality always fails once you add an unnecessary attribute).
💻 Code ▼
SQL — enforcing all 4 constraints on INSERT (Domain, Key, Entity Integrity, Referential Integrity)
CREATE TABLE Student (
  ID INT,
  Name VARCHAR(100) NOT NULL,
  EmailAdd VARCHAR(100) UNIQUE,
  CGPA DECIMAL(3,2),
  Dept CHAR(3),
  PRIMARY KEY (ID),
  FOREIGN KEY (Dept) REFERENCES Department(DeptID),
  CHECK (CGPA >= 0.00 AND CGPA <= 4.00)
);
PRIMARY KEY (ID) enforces both the Key constraint and Entity Integrity (ID can't be null or duplicated). UNIQUE enforces the key constraint on a non-PK candidate key (EmailAdd). CHECK + the declared data type together enforce the Domain constraint. FOREIGN KEY ... REFERENCES enforces Referential Integrity on insert.
SQL — enforcing Referential Integrity on DELETE/UPDATE with cascade options
CREATE TABLE Grades (
  ID INT,
  Ccode CHAR(6),
  Grade VARCHAR(2),
  PRIMARY KEY (ID, Ccode),
  FOREIGN KEY (ID) REFERENCES Student(ID)
    ON DELETE CASCADE
    ON UPDATE CASCADE,
  FOREIGN KEY (Ccode) REFERENCES Course(Ccode)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
);
Deleting a Student row cascades to delete their Grades rows automatically (no orphaned FK). Deleting a Course row referenced by any Grades row is instead blocked (RESTRICT). Note: SET NULL is not usable here for either FK, because both ID and Ccode are part of this table's own composite primary key — Entity Integrity would forbid the null.

d (disjoint) splits entities into non-overlapping groups — think "d"ivide. o (overlapping) looks like a ring that can hold membership in multiple groups at once.
"Total = Two lines"
Double line = Total participation (both start with a doubled sound: "To-tal", "Two"). Single line = Partial, the leftover case.
DKER
The 4 relational integrity constraints in the order the lecture presents them: Domain, Key, Entity integrity, Referential integrity.
Steps 1–7, by logical grouping (not a word mnemonic)
Entities first (1. Regular → 2. Weak), then relationships in shrinking cardinality order (3. N:M → 4. 1:N → 5. 1:1), then leftover attributes (6. Multivalued), then everything connecting 3+ entities (7. N-ary). The order isn't arbitrary — entities must exist before anything can reference them, and N:M relationships need their own table before you can even ask whether a relationship "degrades" to 1:N or 1:1.
