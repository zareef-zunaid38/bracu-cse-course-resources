📖 Theory ▼
Storage & Indexing — Topics 19–21
Heap vs. Sorted File Organization MED

Heap (unordered): records anywhere there's free space. Insert = fast append; search = full linear scan; delete = mark free, may need reorganization.

Sorted (ordered): records kept in physical order by an attribute. Search can binary-search (fast); insert/delete is expensive (shifting to maintain order).

Common error: assuming a heap file allows binary search — it doesn't; binary search needs physical order.
Primary vs. Secondary Index HIGH
Primary (Clustering)Secondary (Non-clustering)
Table orderingPhysically sorted by this keyNot sorted by this key
Count per tableExactly 1Can be many
Usually built onPK — but not alwaysAny frequently-queried attribute
Common trap: "Primary index" ≠ "index on the primary key." It means the index whose key the table is physically sorted by.
Dense vs. Sparse Index HIGH

Dense: every search-key value has an entry — works for primary or secondary indexes.

Sparse: only some values have entries; jump to nearest entry, scan forward — primary indexes only, since it depends on physical sort order.

Why: sparse can't work on a secondary key — an unsorted table gives no "forward" to scan.
Multilevel Indexing → B+ Tree HIGH

A dense index too large for memory gets a hierarchy: one dense inner index on disk (points to records) + sparse outer index(es) in memory on top. This exact idea — sparse on top, dense at bottom — is what a B+ tree formalizes.

B+ Tree Structure & Order Rules HIGH

Balanced multi-level tree. Root/internal nodes = sparse outer index; leaves = dense inner index, linked for sequential scans. Guarantees logarithmic search/insert/delete regardless of data order.

Ordering invariant: for a key in a node, left subtree values < key ≤ right subtree values.

MaxMin
ChildrenRoot/internal: n · Leaf: 0Root: 2 (if not also a leaf) · Internal: ⌈n/2⌉
Keysn − 1Root: 1 · Leaf/Internal: ⌈n/2⌉ − 1
B+ Tree Insertion HIGH
  1. Walk down to the correct leaf.
  2. Room? Insert in sorted order — done.
  3. Full? Split in half: lowest key of new right node sent up to parent.
  4. Parent full too? Split it the same way, propagate; if root splits, tree height increases.
Key distinction: a leaf split copies the separator key up (it stays in the right leaf). A non-leaf split moves it up only — no duplicate left behind.

Odd order n biases splits left or right by one extra value — pick one convention and hold it for the whole tree.

B+ Tree Deletion — 5 Cases HIGH
CaseConditionAction
1Leaf > min keysJust remove (1b: also in internal node → replace with lowest value from right-most subtree)
2Leaf = min, sibling > minBorrow through parent (2a left / 2b right)
3Leaf = min, sibling = min, parent > minMerge with sibling, remove parent key
4Parent also = minMerge as Case 3, deficiency propagates up (4a borrow / 4b merge one level up)
5Propagates to rootMerge to root; if root key deleted, replace with lowest value from right-most subtree first — tree height shrinks
Rule to not forget: any deleted key that's also copied in an internal node must be replaced with the lowest value from its right-most subtree — never left blank.
Hashing (secondary structure) LOW

Buckets assigned by a hash function on the search key. Overflow (shared key values, or uneven distribution) handled by forward/overflow chaining only. Best case O(1), worst case degrades to full scan — no guaranteed bound, unlike B+ trees.

Query Processing & Optimization — Topic 22
4-Step Processing Pipeline MED
  1. Query Compilation — SQL → relational algebra expression
  2. Query Optimization — modify RA + choose execution strategy
  3. Code Generation — glue together RA building-block implementations
  4. Query Execution — run generated code, return result
"Optimization" is misleading — the result is improved, not guaranteed mathematically optimal.
Pipelining & Materialization MED

Operations stream one tuple at a time — low buffering, better throughput. Joins break this: at least one branch must be fully buffered (materialized) to match against the other's stream; high volume forces it to disk.

Algorithm Strategies Per Operation HIGH
OperationStrategies
Selection (single attr)Table scan (linear/binary-if-sorted) or index-based search (preferred)
Selection (range, tree index)Index seek then index scan
Selection (AND)In practice: chain of single-attribute selections (best reorder/push-down flexibility)
JoinNested-loop, merge join (sorts + materializes both), hash join
Index-based joinOnly if both relations index the join attribute — intersect index node values
ProjectionOnly ONE strategy: iterative strip-as-you-go
AggregateSplit-Apply-Combine; split stage pipelined via running group function
Heuristic Algebraic Optimization Rules HIGH
Cascade of σσc1 AND c2(R) ≡ σc1(σc2(R))
Commutativity of σσc1(σc2(R)) ≡ σc2(σc1(R))
Cascade of πonly the last projection matters
Commuting σ with πallowed if σ only uses attributes already projected
Commutativity of ⋈, ×R ⋈c S ≡ S ⋈c R
Commuting σ with ⋈allowed if c uses only one side's attributes
(σ,×) → ⋈σc(R × S) ≡ R ⋈c S, when c is exactly the join condition

Application procedure: cascade → push selects/projects down to the leaves → order most-restrictive select first → convert (σ,×) into ⋈ → group sub-trees for single-algorithm execution.

Careful: pushing a selection down (which relation needs it) and reordering which join happens first are two separate transformations — easy to conflate, and a step that only does the first hasn't finished the optimization.
Cost-Based Optimization MED

Database catalog: per-relation metadata (size, record count, block count, index structure, selectivity, etc.). Histograms: without one, optimizer assumes uniform distribution — often wrong. Cost function: weighted sum of disk access, buffer use, computation, communication — candidates evaluated against catalog+histogram data. Search space is exponential, so dynamic programming + pruning is used, not exhaustive search.

Transactions — Topic 23
ACID Properties HIGH
PropertyRequirementEnforced by
AtomicityAll or nothingRecovery subsystem
ConsistencyValid state → valid state (before/after only)Application/constraint logic
IsolationNo visibility of uncommitted workConcurrency control subsystem
DurabilityCommitted changes survive failuresRecovery subsystem
Exam framing rule: Atomicity + Durability → recovery-system concern; Isolation → concurrency-control concern; Consistency → application-logic/constraint concern.
Transaction States MED

Active → Partially committed → Committed → Terminated (success path), or Active/Partially committed → Failed → Terminated (failure path). A failed transaction may be legitimately resubmitted as a brand-new transaction.

Causes of Transaction Failure LOW

System crash · transaction/system error (overflow, bad params, bug) · locally-detected error (business rule, e.g. insufficient balance) · concurrency-control enforcement (serializability/deadlock) · disk failure · physical catastrophe.

Log-Based Recovery — UNDO/REDO HIGH

Log records: <Ti start>, <Ti, X, old, new>, <Ti commit>.

The rule: <Ti commit> present → REDO Ti (replay to guarantee durability). Absent → UNDO Ti (roll back, since nothing is durable).

undo(Ti): walk log backward from Ti's last record, restore old values. redo(Ti): walk log forward from Ti's first record, re-apply new values.

Concurrency Control — Topic 24
The 5 Concurrency Problems HIGH
ProblemWhat happens
Lost UpdateBoth read before either writes; one write overwrites the other
Temporary Update / Dirty ReadRead an uncommitted value; writer later rolls back
Incorrect SummaryAggregate spans a concurrent partial update
Non-Repeatable ReadSame row, re-read, different value
Phantom ReadSame query, re-run, different row set
Distinction to nail: Non-Repeatable Read = value change on the same row. Phantom Read = row-set change on the same query.
SQL Isolation Levels HIGH
LevelDirty ReadNon-RepeatablePhantom
SerializablePreventsPreventsPrevents
Repeatable ReadPreventsPreventsAllows
Read CommittedPreventsAllowsAllows
Read UncommittedAllowsAllowsAllows
Caveat easy to miss: Lost Update and Incorrect Summary aren't on this table at all. Only Serializable prevents them by forcing full serial behavior; anything below it needs extra locking/application discipline.
Two-Phase Locking (2PL) HIGH

Growing: acquire locks only, no release. Shrinking: starts at first release, only release from then on. Lock point = moment of final lock acquired.

SX
CompatibleIncompatible
VariantRule
Strict 2PLX-locks held to commit/abort; S can release earlier — no cascading rollback
Rigorous 2PLAll locks (S+X) held to commit — stronger than strict
Conservative 2PLAll locks acquired upfront — deadlock-free, low concurrency
Deadlock — Conditions & Handling MED

Necessary conditions (all 3): Hold-and-Wait, No Preemption, Circular Wait.

Strategies: Avoidance (fixed lock order, finer granularity) · Detection (Wait-For Graph, cycle = deadlock) · Prevention (Wait-Die / Wound-Wait by timestamp) · Recovery (pick lowest-cost victim, rollback) · Timeout (simple, can misfire/starve).

SchemePreemptive?Rule
Wait-DieNoOlder waits for younger; younger requesting older's resource aborts+restarts
Wound-WaitYesOlder force-aborts younger holding what it needs; younger waits for older
Aborted/restarted transactions keep their original timestamp — prevents starvation.
MVCC LOW

Keeps multiple versions so readers/writers don't block. Timestamp-ordering: rollback a read/write that would violate the timestamp ordering of prior reads/writes.

MV2PL with Certify Locks is OUT OF SCOPE (confirmed 2026-09-13) — the official Final Notice caps Lecture 9 at Pages 1–28; MV2PL is page 29 of the 30-page deck. Timestamp-ordering (pages 26–28) is the only MVCC technique in scope.
Graph-Based Protocol / Tree Protocol LOW

Fixed access order (acyclic graph) instead of growing/shrinking. Conflict-serializable, deadlock-free, but access order must be fixed in advance and cascading rollback is still possible.

Tree Protocol rule: X-locks only; every lock after the first must be on a child of an item already locked by that transaction — must hold the parent specifically, not just any ancestor.
❓ Short Questions ▼

Tap a question to reveal the answer. Try to recall first.

What's the main tradeoff between a heap file and a sorted file?MED
Heap: fast append, but search needs a full linear scan. Sorted: search can binary-search, but insert/delete is expensive since order must be maintained.
What is the defining property of a primary index?HIGH
The table is physically sorted by that index's search key — usually but not necessarily the primary key.
Why can a sparse index only be built on a primary index?HIGH
Sparse indexes rely on scanning forward from the nearest indexed entry — only works if the table is physically sorted by that key, which is exactly what "primary" means.
In a B+ tree of order n, what's the max keys per node and min keys in a leaf/internal node?HIGH
Max = n − 1. Min (leaf/internal) = ⌈n/2⌉ − 1. Root min keys = 1.
When a leaf splits during insertion, what happens to the separator key sent to the parent — and how does that differ from a non-leaf split?HIGH
Leaf split: the key is copied — it stays in the new right leaf too. Non-leaf split: the key is moved up only, no duplicate left in either child.
During B+ tree deletion, when a deleted key also appears as a copy in an internal node, what must replace that copy?HIGH
The lowest value from that key's right-most subtree — never just an empty removal.
What is the only overflow-handling method for hash indexing marked suitable for DB use, and why does overflow happen at all?LOW
Forward/overflow chaining. Overflow happens because multiple records can share a key value, or the hash function distributes keys unevenly.
Why does a join operation break query pipelining?MED
At least one branch must be fully buffered (materialized) to be matched against the other side's incoming stream — forced to disk if volume is too high.
What is the one strategy for implementing Projection, and why is it the only one?MED
Iterative, strip-as-you-go — unwanted attributes are removed immediately per tuple, never batched first (would add buffering overhead). Unlike selection/join, no alternative exists.
Why does a DBMS keep histograms in addition to the catalog?MED
Without one, the optimizer must assume a uniform value distribution — often wrong. A histogram gives the true distribution, so selectivity estimates (and hence join order/selection choices) are accurate.
What are the four ACID properties and which subsystem enforces each?HIGH
Atomicity (recovery — all-or-nothing), Consistency (application logic — valid state to valid state), Isolation (concurrency control — no interference), Durability (recovery — committed persists).
How do you decide UNDO vs. REDO for a transaction after a crash?HIGH
Check for <Ti commit> in the log. Present → REDO. Absent → UNDO.
A double-booking scenario (two users booking the last seat concurrently) violates which ACID property, and why not Durability?MED
Isolation — the transactions must not both proceed unaware of each other. Not Durability because nothing committed is lost afterward; the problem occurs during concurrent execution, before either commits.
What's the difference between Lost Update and Temporary Update (Dirty Read)?HIGH
Lost Update: both read before either writes, so one write silently overwrites the other. Temporary Update: a transaction reads another's uncommitted value, and that writer later rolls back.
Which isolation level prevents Dirty Read and Non-Repeatable Read but still allows Phantom Read?HIGH
Repeatable Read. Only Serializable prevents all three.
Do isolation levels below Serializable guarantee prevention of Lost Update / Incorrect Summary?MED
No — those two aren't on the standard three-phenomena table at all; preventing them below Serializable needs extra locking/application discipline.
In 2PL, what is the "lock point"?HIGH
The moment a transaction acquires its final lock — the boundary between growing (acquire only) and shrinking (release only) phases.
What's the key difference between Wait-Die and Wound-Wait?MED
Wait-Die (non-preemptive): younger transaction aborts itself rather than block an older one. Wound-Wait (preemptive): older transaction force-aborts a younger one holding what it needs.
What are the three necessary conditions for deadlock?MED
Hold-and-Wait, No Preemption, Circular Wait.
In the Tree Protocol, what rule governs which item a transaction can lock next?LOW
X-locks only; every lock after the first must be on a child of an item the transaction already holds — it must specifically hold that child's parent, not just any ancestor.
🧮 Analytical Questions ▼
Q1 Insert 4, 10, 7, 12, 1, 5, 2, 25, 15, 9, 18, 20 into a B+ tree of order n = 4. Trace every split. HIGH ▼
1
4, 10, 7 → single leaf [4,7,10] (max 3 keys, no split yet).
2
Insert 12 → leaf full, splits: root [10], leaves [4,7] | [10,12].
3
Insert 1 → fits: [1,4,7] | [10,12].
4
Insert 5 → left full, splits: root [5,10], leaves [1,4] | [5,7] | [10,12].
5
Insert 2, 25 → both fit: [1,2,4] | [5,7] | [10,12,25].
6
Insert 15 → right leaf full, splits: root [5,10,15], leaves [1,2,4] | [5,7] | [10,12] | [15,25].
7
Insert 9, 18 → both fit: [1,2,4] | [5,7,9] | [10,12] | [15,18,25].
8
Insert 20 → rightmost leaf full and splits, AND the root (now full at [5,10,15]) splits too → height grows to 2: new root [15], left subtree root [5,10] (4 leaves), right subtree root [20] (leaves [15,18] | [20,25]).
Key insight: most splits stay leaf-only; step 8 is the case worth practicing — a leaf split cascades into a root split, increasing tree height. That's exactly where the leaf-copies-up vs. internal-moves-up distinction matters.
Exam note: this is the exact question shape Quiz 3 used (order-3 tree, 8 values, draw state after each insertion). Practice with a fresh sequence, not just this memorized one.
Q2 B+ tree deletion: walk a key through a borrow (Case 2) and then a merge (Case 3) scenario. HIGH ▼
1
Target leaf is at exactly min keys (⌈n/2⌉ − 1). Check its immediate sibling first.
2
Sibling has more than min → Case 2, borrow: the borrowed key moves through the parent (highest of left sibling moves up if borrowing left; lowest of right sibling moves up if borrowing right).
3
If instead the sibling is also at min, but the parent has more than min → Case 3, merge: merge target leaf with its sibling into one node, then remove the now-redundant separator key from the parent.
4
If the deleted key was also copied in an internal node anywhere in this process, replace that copy with the lowest value from its right-most subtree — do not delete it outright.
Key insight: Cases 2 vs. 3 hinge entirely on whether the sibling has spare keys. Case 4/5 only trigger when the deficiency can't be absorbed at the leaf level and must propagate to the parent (4) or all the way to the root (5).
Q3 Given the log — <T1 start>, <T1,A,500,600>, <T1 commit>, <T2 start>, <T2,B,1000,1200>, <T3 start>, <T3,C,700,800>, <T3 commit>, then a system crash — find the final values of A, B, C. HIGH ▼
1
Scan the log per transaction for <Ti commit>.
2
T1 has <T1 commit> → REDO → A = 600 (new value stands).
3
T2 has no commit record → UNDO → B = 1000 (old value restored).
4
T3 has <T3 commit> → REDO → C = 800 (new value stands).
Key insight: commit record present → new value stands (redo to guarantee it); commit record absent → old value stands (undo whatever partial writes happened). Works identically whether the case is pure-UNDO, pure-REDO, or mixed.
Q4 Optimize: SELECT Lname FROM Employee, Project, Works_On WHERE Pname='Aquarius' AND Pnumber=Pno AND Essn=Ssn AND Bdate>'1957-12-31'. MED ▼
1
Start: one big conjunctive σ over a Cartesian product chain of all three relations.
2
Cascade + push down: split the AND into 4 conditions, push each above only the single relation it needs (Bdate above Employee, Pname above Project); Pnumber=Pno and Essn=Ssn stay as join conditions.
3
Reorder joins: compute the smaller/more-filtered Project⋈Works_On (via Pnumber=Pno) first, then join that result to the Bdate-filtered Employee via Essn=Ssn.
4
Convert remaining (σ,×) pairs into actual ⋈ operators.
5
Push projections down too — carry only the columns later joins actually need, not full rows.
Exam note: steps 2 and 3 are the pair examiners most often test as if they were one step. Pushing a selection down (step 2) tells you *where* a filter sits; reordering joins (step 3) is a separate decision about *which join happens first*.
Q5 T1: Lock-X(A), Read(A), Write(A), Lock-S(B), Read(B), Unlock(A), Unlock(B). Meanwhile T2 tries Read(A) while T1 still holds it uncommitted. What happens, and where is T1's lock point? HIGH ▼
1
T1's lock point is at Lock-S(B) — its final lock acquisition, right before it starts unlocking.
2
T2's Read(A) happens while T1 still holds an uncommitted X-lock on A → this is a dirty read.
3
T2 must roll back. Once T1 releases A, T2 (or any other transaction) can legitimately Lock-X(A) and proceed.
Key insight: any read of an item another transaction currently holds under an uncommitted X-lock is a dirty read, full stop — the exam-relevant skill is spotting which reads in a trace fall before vs. after the writer's unlock step.
Q6 T1 holds Account A and wants B; T2 holds Account B and wants A. Build the Wait-For Graph and determine whether this is a deadlock. MED ▼
1
Draw an edge T1 → T2 (T1 waits on a resource T2 holds).
2
Draw an edge T2 → T1 (T2 waits on a resource T1 holds).
3
A cycle exists (T1 → T2 → T1) → deadlock confirmed.
Key insight: this generalizes directly to N transactions — an edge exists wherever one transaction blocks on a resource another holds, and any cycle anywhere in the graph (no minimum length beyond 2) is sufficient to declare deadlock.
Q7 Teller (T1) reads Customer X's balance ($150), deducts $100 (uncommitted, now $50). Auditor (T2) re-reads and sees $50. T1 rolls back (balance reverts to $150). T2 inserts new Customer Y ($80) and re-runs its "balance < $100" report, now seeing Y. Identify both problems, the shared violated property, the prevention, and the recovery technique. HIGH ▼
1
T2 reading T1's uncommitted $50 → Dirty Read (Temporary Update).
2
T2's report query returning a new row (Customer Y) on re-run → Phantom Read.
3
Both trace back to a violation of Isolation.
4
Prevention: run at Serializable isolation, so the transactions behave as if sequential.
5
Recovery technique needed for T1's rollback: an undo log — it retains the old value ($150), exactly what's needed to revert the uncommitted deduction.
Exam note: this is the exact scenario shape Quiz 4 used (a multi-part concurrency scenario). The reported weak point was live scenario→named-problem recognition under time pressure, not the underlying concept — drill naming the problem fast from a one-line description.
∑ Mathematics ▼
B+ Tree — Max/Min Keys and Children (order n)
Max keys = n − 1 Max children = n (root/internal) Min keys (leaf/internal) = ⌈n/2⌉ − 1 Min keys (root) = 1 Min children (internal) = ⌈n/2⌉ Min children (root) = 2*
n = order (max children an internal/root node can have). *Root minimum children of 2 applies only once the root is no longer also a leaf (tree has grown past a single node).
Ex Worked: for order n = 4, compute max keys, min keys (leaf/internal), and min children (internal). HIGH ▼
1
Max keys = n − 1 = 4 − 1 = 3.
2
Min keys (leaf/internal) = ⌈n/2⌉ − 1 = ⌈2⌉ − 1 = 2 − 1 = 1.
3
Min children (internal) = ⌈n/2⌉ = ⌈2⌉ = 2.
Pattern: this matches Q1's trace above — every leaf held between 1 and 3 keys before splitting at 4, confirming the max/min bounds hold throughout.
Ex Worked: for order n = 3 (Quiz 3's actual order), compute the same bounds. MED ▼
1
Max keys = n − 1 = 3 − 1 = 2.
2
Min keys (leaf/internal) = ⌈n/2⌉ − 1 = ⌈1.5⌉ − 1 = 2 − 1 = 1.
3
Min children (internal) = ⌈n/2⌉ = ⌈1.5⌉ = 2.
Pattern: order 3 splits far more often than order 4 (max 2 keys per leaf vs. 3) — expect more, smaller splits when practicing at this order.
💻 Relational Algebra (Query Optimization) ▼

SQL itself (Topics 3–9) is lab-only and not on this Final. Relational algebra shows up here only as the notation query-optimization questions are answered in.

RA — single-table optimization (push selection, project early)
-- Query: SELECT Fname, Lname, Ssn FROM EMPLOYEE
--        WHERE address='Merul Badda' AND Salary>50000

E1 = π_Fname,Lname,Ssn,Address,Salary (EMPLOYEE)
E2 = σ_Salary>50000 ( σ_Address='Merul Badda' (E1) )
E3 = π_Fname,Lname,Ssn (E2)
Even a single-table query benefits from an early projection to a superset of needed columns before filtering, then a final projection down to exactly the SELECT list.
RA — multi-join optimization pattern
-- Pattern for a 3-way join (Department ⋈ Project ⋈ Employee),
-- one selection condition per relation:

E1 = σ_cond1 ( π_neededCols (Relation1) )
E2 = σ_cond2 ( π_neededCols (Relation2) )
E3 = σ_cond3 ( π_neededCols (Relation3) )

Result = π_finalCols ( (E1 ⋈ E2) ⋈ E3 )
Every selection and projection resolved at the leaf level before any join — generalizes the single-table pattern to any number of joined relations.

🧠 Mnemonics & Memory Aids ▼
ACID → who fixes it
A + D → Recovery ("crash-related"). I → Concurrency Control ("crowd-related"). C → Application logic (nobody else's job).
Commit? Redo. No commit? Undo.
The entire UNDO/REDO decision in six words — check the log for <Ti commit>, nothing else matters.
"Die is giving up, Wound is attacking"
Wait-Die: the younger transaction gives up (aborts itself) rather than make an older one wait. Wound-Wait: the older transaction actively wounds (force-aborts) the younger one.
Value vs. Set
Non-Repeatable Read = a value changed. Phantom Read = the row set changed. Same trigger (re-read/re-run), different casualty.
Grow first, give later
2PL: acquire everything you need before you release anything. The instant you release your first lock, you can never acquire another.
