📖 Theory ▼
Process Concept & PCB HIGH

A process is a program in execution. A program is passive (a file on disk); a process is active (loaded into memory, with a program counter, stack, and resources). One program binary can run as multiple simultaneous processes.

The OS represents each process using a PCB (Process Control Block) — a kernel data structure with six field categories:

  • Process state — new / ready / running / waiting / terminated
  • Program counter — address of the next instruction
  • CPU registers — all register values; saved on context switch
  • Memory management info — page tables, base/limit registers
  • I/O status info — open file list, allocated I/O devices
  • Accounting info — CPU time used, time limits, job numbers
Exam note: "What is saved during a context switch?" — answer: CPU registers + program counter (the CPU state fields of the PCB). Do not say "the whole PCB"; memory and I/O info are also there but the CPU state is what changes per switch.
Process States & Transitions HIGH

A process passes through five states. Every state has specific triggers for entry and exit.

TransitionTrigger
new → readyOS admits the process into memory
ready → runningShort-term scheduler dispatches the process
running → waitingProcess issues I/O request or waits for an event
waiting → readyI/O completes or event occurs
running → readyTimer interrupt (preemption by OS)
running → terminatedProcess calls exit() or is killed
Critical distinction: A process in WAITING is blocked — it cannot use the CPU even if the CPU is free. A process in READY is capable of running but is waiting for the scheduler. The scheduler never touches a WAITING process directly.
fork(), exec(), wait() HIGH

fork() creates a child process as an exact duplicate of the parent. Both processes resume from the line after fork(). The return value distinguishes them:

  • In child: returns 0
  • In parent: returns child's PID (positive integer)
  • On error: returns -1

exec() replaces the calling process's memory image with a new program. If exec() succeeds, the caller does not return — the new program takes over.

wait() blocks the parent until a child terminates and collects the child's exit status, releasing the child's PCB entry.

Exam note: The classic question shows code with one or more fork() calls and asks how many processes are created or what is printed. Trace each fork() call and track PID return values separately for each process branch.
Zombie vs Orphan HIGH
StateCauseEffectResolution
ZombieChild exited; parent has not called wait()Child PCB remains in process table — wastes a process table entryParent calls wait(); or SIGCHLD handler
OrphanParent terminated before childChild loses its parent referenceinit (PID 1) adopts the child and periodically calls wait()
Why zombie exists: The OS guarantees a parent can always retrieve a child's exit code. To uphold that guarantee, the PCB must persist until the parent acknowledges the exit — even after the child has stopped running.
IPC — Shared Memory vs Message Passing HIGH

Processes are isolated by default (separate address spaces). IPC provides two fundamental models for cooperating processes to exchange data.

DimensionShared MemoryMessage Passing
MechanismOS maps a shared region into both address spaces; processes read/write directlyProcesses call send(msg) and receive(msg); kernel mediates
SpeedFast — no kernel involvement per operation after setupSlow — every exchange is at least 2 system calls
SynchronizationManual — programmer must prevent race conditionsAutomatic — kernel serializes access
Best forLarge data on the same machineSmall messages or distributed systems
Scheduling Queues & Schedulers MED

Processes move between three queues during their lifetime:

  • Job queue — all processes in the system (including on disk)
  • Ready queue — processes in main memory, ready and waiting for CPU
  • Device queue — processes waiting for a specific I/O device (one per device)

Three schedulers manage the queues:

SchedulerAlso CalledFrequencyRole
Long-termJob / admission schedulerInfrequentControls degree of multiprogramming (how many processes in memory)
Short-termCPU scheduler / dispatcherVery frequent (ms)Selects which ready process gets the CPU next
Medium-termSwapperModerateSwaps processes in/out of memory (virtual memory systems)
Context Switch MED

When the CPU switches from process A to process B: (1) save A's CPU state (registers, PC) into A's PCB; (2) load B's CPU state from B's PCB; (3) resume B from where it left off.

Context switch time is pure overhead — no user-level work is performed during the switch. Typical cost: a few microseconds. This is why a very short Round Robin time quantum is harmful: more time is spent switching than executing.

Sockets LOW

A socket is a communication endpoint identified by IP address : port number. Sockets support communication between processes on different machines (or the same machine via loopback 127.0.0.1).

  • TCP socket — connection-oriented; reliable, ordered, error-corrected
  • UDP socket — connectionless; no delivery guarantee, lower overhead

Ports below 1024 are reserved for system services and require root privileges to bind.

Message Passing Variants LOW
  • Naming: Direct (processes name each other) vs Indirect (messages go to/from a mailbox/port)
  • Synchronization: Blocking send (sender waits for receipt) vs Non-blocking send (sender continues immediately). Same distinction applies to receive.
  • Buffering: Zero capacity (rendezvous — sender blocks until receiver ready) / Bounded capacity (sender blocks when queue full) / Unbounded capacity (sender never blocks)
❓ Short Questions ▼

Tap a question to reveal the answer. Try to answer it first.

What is a process? How is it different from a program? HIGH
A process is a program in execution. A program is passive — it is a binary file stored on disk. A process is active — it is that program loaded into memory with its own program counter, stack, heap, and allocated resources. One program can be the basis of multiple processes simultaneously (e.g., two browser windows running the same executable).
List all five process states. What triggers the transition from RUNNING to WAITING? HIGH
The five states are: New, Ready, Running, Waiting, Terminated. The transition from Running to Waiting is triggered when the process issues an I/O request or waits for an event (e.g., disk read, user input, a signal). The process cannot proceed until that I/O completes or the event occurs.
What does fork() return in the parent, in the child, and on error? HIGH
  • In the child: fork() returns 0
  • In the parent: fork() returns the child's PID (a positive integer)
  • On error: fork() returns -1 (no child is created)
Both parent and child continue executing from the line immediately after the fork() call.
What is a zombie process? What causes it and why is it a problem? HIGH
A zombie is a process that has terminated (called exit()) but whose PCB entry still exists in the process table because the parent has not yet called wait() to collect the exit status. It is a problem because zombie entries accumulate in the process table, which has a fixed size — enough zombies will eventually prevent any new process creation.
What is the key difference between shared memory and message passing IPC? HIGH
Shared memory is faster — processes read and write a shared memory region directly with no kernel involvement per operation — but the programmer must manually synchronize access to prevent race conditions. Message passing routes every exchange through the kernel (send/receive system calls), making it slower but automatically safe. Shared memory suits large data transfers on one machine; message passing suits distributed systems or small messages.
What is a context switch? Why is it described as overhead? MED
A context switch is the CPU operation of saving the state of the current process (registers, program counter) into its PCB, then loading the state of the next process from its PCB. It is pure overhead because no user-level computation is performed during the switch — the CPU is doing bookkeeping, not useful work. Frequent context switching wastes CPU cycles.
What is an orphan process? How does UNIX resolve it? MED
An orphan process is one whose parent terminated before it did. Without a parent, no process would call wait() on it, and it would eventually become a zombie. UNIX resolves this by re-parenting the orphan to init (PID 1), which periodically calls wait() to clean up any children that have exited.
What are the differences between an ordinary pipe and a named pipe (FIFO)? MED
An ordinary pipe is unidirectional, works only between a parent and its child, and is temporary (disappears when the processes end). A named pipe (FIFO) can be bidirectional, works between any two processes (no relationship required), and is persistent — it exists as a file in the filesystem even after the processes exit.
What six categories of information does a PCB contain? MED
Process state · Program counter · CPU registers · Memory management info · I/O status info · Accounting info. The first three together form the CPU state — the part that must be saved and restored on every context switch.
🧮 Analytical Questions ▼
Q1 A process calls fork() twice in sequence. How many processes exist in total after both calls execute? Justify your answer. HIGH ▼
1
Start: 1 process (the original, call it P0).
2
P0 calls fork(). This creates child P1. Now 2 processes exist: P0 and P1. Both resume after the first fork() call.
3
Both P0 and P1 reach the second fork() call independently. P0 creates P2. P1 creates P3. Each process that reaches fork() creates one child.
4
Total after both forks: 4 processes — P0, P1, P2, P3.
Pattern: n sequential fork() calls (where every process calls every fork()) → 2n total processes. Each fork doubles the current count.
Exam note: The question may instead specify that only the parent calls fork() each time (children return immediately). In that case: n forks → n+1 processes (original + n children). Always read which branch the next fork() is in.
Q2 For each scenario below, identify the process state and the transition trigger: (a) a process finishes an I/O request; (b) the OS timer interrupt fires; (c) the scheduler selects a process from the ready queue; (d) a process calls exit(). HIGH ▼
a
I/O completes: Process was in WAITING. Transition: WAITING → READY. Trigger: I/O completion event. The process does not go directly to RUNNING — it re-enters the ready queue and waits for the scheduler.
b
Timer interrupt fires: Process was RUNNING. Transition: RUNNING → READY. Trigger: preemption by OS (time slice expired). The process is returned to the ready queue without any I/O involvement.
c
Scheduler selects a process: Process was in READY. Transition: READY → RUNNING. Trigger: short-term scheduler dispatch. This is the only way a process enters the RUNNING state.
d
Process calls exit(): Process was RUNNING. Transition: RUNNING → TERMINATED. Trigger: process voluntarily exits or is killed by signal. PCB is retained as a zombie until the parent calls wait().
Key rule: The only entry point to RUNNING is from READY. The scheduler never promotes a WAITING process directly to RUNNING — I/O completion moves it to READY first.
Q3 A child process exits, but its parent is in an infinite loop and never calls wait(). Separately, a parent exits while its child is still sleeping. Describe what happens in each case. MED ▼
1
Case 1 — Parent never calls wait(): The child terminates and transitions to TERMINATED, but its PCB entry is not freed. The child becomes a zombie. It will remain a zombie for as long as the parent runs. If the parent eventually exits, init inherits the zombie and calls wait() to clean it up.
2
Case 2 — Parent exits before child: The child's parent reference becomes invalid. UNIX re-parents the child to init (PID 1). Init periodically calls wait(), so when the child eventually exits, init will collect it — no zombie remains.
Summary: Zombie = child outlives collection. Orphan = child outlives parent. In both cases the child continues to exist in the process table — the difference is what happens next. An orphan is adopted and cleaned up. A zombie waits indefinitely for a parent that may never call wait().
∑ Mathematics ▼

Chapter Process has minimal formal math. The only quantitative pattern is the fork() process count formula.

Process Count — All branches fork
Total processes = 2^n
Where n = number of fork() calls, assuming every existing process executes every fork().
Process Count — Only parent forks each time
Total processes = n + 1
Where n = number of fork() calls, and only the parent process reaches each fork() (children exit or exec immediately).
Ex Given the code: fork(); fork(); fork(); — how many processes are created in total? HIGH ▼
1
n = 3 fork() calls. All processes reach all fork() calls (no conditional branching).
2
Apply: 23 = 8 processes total.
3
Verification: after fork 1 → 2 processes; after fork 2 → 4; after fork 3 → 8. Each fork doubles the count.
Pattern: Look for if/else branching around fork() calls. If children exit in the if-branch before reaching the next fork(), they do not contribute to the next doubling. Trace carefully.
💻 Code ▼
C — fork() basic pattern
#include <unistd.h>
#include <stdio.h>
#include <sys/wait.h>

int main() {
    pid_t pid = fork();

    if (pid == 0) {
        // CHILD: fork() returned 0
        printf("Child PID = %d\n", getpid());
    } else if (pid > 0) {
        // PARENT: fork() returned child's PID
        printf("Parent PID = %d, Child PID = %d\n", getpid(), pid);
        wait(NULL);   // blocks until child exits; prevents zombie
    } else {
        // ERROR: fork() returned -1
        perror("fork failed");
        return 1;
    }
    return 0;
}
What to notice: pid == 0 always means you are in the child. pid > 0 always means you are in the parent, and that positive value is the child's PID. The wait(NULL) call is critical — omitting it leaves the child as a zombie after it exits. The parent and child both continue from after the fork() call, which is why both branches execute.
C — pipe() between parent and child
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

int main() {
    int fd[2];
    pipe(fd);          // fd[1] = write end, fd[0] = read end

    pid_t pid = fork();

    if (pid == 0) {
        // CHILD reads from pipe
        close(fd[1]);          // child does not write; close write end
        char buf[64] = {0};
        read(fd[0], buf, sizeof(buf));
        printf("Child received: %s\n", buf);
        close(fd[0]);
    } else {
        // PARENT writes to pipe
        close(fd[0]);          // parent does not read; close read end
        const char *msg = "hello from parent";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);
        wait(NULL);
    }
    return 0;
}
What to notice: fd[1] is always the write end; fd[0] is always the read end — memorize this. Each process must close the end it does not use. If the parent does not close fd[0] and the child does not close fd[1], the child's read() will block indefinitely — the kernel sees the write end as still open and will not signal EOF. Forgetting to close unused pipe ends is the most common pipe bug.

🧠 Mnemonics & Memory Aids ▼
Never Rest — Run While Tired
New → Ready → Running → Waiting → Terminated. The five states in order. Note: RUNNING can skip back to READY (interrupt) or go to WAITING (I/O) before reaching TERMINATED.
Zero child. Positive parent. Negative nobody.
fork() return values: 0 in the child, positive PID in the parent, -1 (negative) when fork fails and no child was created. Say it once before entering the exam.
PCB = "PPCMIA"
Process state · Program counter · CPU registers · Memory management info · I/O status info · Accounting info. The first three are the CPU state saved on every context switch.
Zombie = orphaned collection. Orphan = orphaned parent.
A zombie's exit status collection was orphaned — the parent never called wait(). An orphan's parent process was orphaned — the parent exited first. Two different things that got orphaned.
fd[1] writes, fd[0] reads. 1 → 0, like a countdown.
In pipe(fd): fd[1] is the write end, fd[0] is the read end. Think of data flowing from 1 down to 0. Close whichever end you are not using, or reads will block forever.
Add your own. The best mnemonic is the one you invented during study, not one you read here.
