📖Theory▼
Module 1 — Process
Dual Mode Operation & System Calls HIGH

Mode bit: user mode (restricted) vs kernel mode (full access). A trap switches user→kernel so the OS can safely perform privileged work. System calls are the interface for this — know the 6 categories (Process Control, File Manipulation, Device Manipulation, Info Maintenance, Communication, Protection) with a Windows/Linux example each.

Gap patched: this whole block was missing from the original notes — slide-confirmed, ~6 slides of content. Newly added tonight.
PCB & Process States HIGH

5 states: new, ready, running, waiting, terminated. PCB has 6 field categories — don't forget "CPU scheduling info" (priorities, queue pointers), the category most often dropped.

Exam note: "What is saved during a context switch" = CPU registers + program counter, the CPU-state portion of the PCB.
fork() / exec() / wait() — Zombie & Orphan HIGH

fork() returns 0 in child, child's PID in parent, -1 on error. Zombie = child exited, parent hasn't called wait(). Orphan = parent terminated first, child reparented to init.

Trending since Su25: zombie/orphan identification appeared in 3 of the last 4–5 sittings — a newer emphasis, don't underweight it relative to older PYQs.
IPC: Shared Memory vs Message Passing MED

Shared memory = fast, no kernel per-op, manual sync required. Message passing = slower (kernel-mediated), automatic sync. Naming/synchronization/buffering variants are textbook-only, not slide-covered — lower priority than the core comparison.

Pipes & Sockets LOW

Ordinary pipe = unidirectional, parent-child only. Named pipe (FIFO) = bidirectional, any processes, persistent. Not found anywhere in the slide deck — textbook-only, lowest priority in this module if time is short.

Module 2 — Threads
Concurrency vs Parallelism HIGH

Concurrency = multiple tasks make progress (possibly interleaved on one core). Parallelism = literally simultaneous, requires multiple cores. Data parallelism (same op, split data) vs task parallelism (different independent tasks).

Gap patched: entire Multicore Programming section was missing — newly added, slide-confirmed.
Threading Models: Many-to-One / One-to-One / Many-to-Many MED

One-to-one (Linux/Windows default) allows true parallelism, blocking doesn't affect other threads, but costs one kernel thread per user thread. Many-to-one is fast but one blocking call stalls everything. Was a 2023–24 exam fixture, now less common but still in scope.

Thread Pools & Implicit Threading MED

5 implicit-threading methods: Thread Pools, Fork-Join, OpenMP, GCD, Intel TBB (Fork-Join was missing from original notes — patched). Pools avoid per-request thread-creation overhead with a bounded, reusable set of workers.

Threading Issues MED

fork() in multithreaded programs: duplicate-all-threads vs duplicate-calling-thread-only (Linux default is the latter). Signal routing: synchronous→faulting thread, asynchronous→any unblocked thread. Cancellation: deferred (safe, default) vs asynchronous (unsafe). Thread-specific data (patched — was missing) is the 5th issue on the slide's list.

Module 3 — CPU Scheduling
TAT / WT / RT Formulas HIGH

TAT = CT − AT. WT = TAT − BT. RT = first CPU time − AT. Know these cold — every Gantt-chart question needs them.

MLFQ — Two Competing Rule Sets HIGH

OSTEP's 5 rules (periodic priority boost after time S) vs. the slide's own worked examples, which promote a process one queue level after each I/O operation instead. Both appear in course material — read the question carefully for which mechanism it specifies.

Slide's own inconsistency: textbook 3-queue example says Q2=FCFS, but the professor's worked "Problem 1/2" use Q2=Round Robin(q=8). If a question doesn't specify, don't assume — follow what the question states.
FCFS / SJF / SRTF MED

FCFS: convoy effect. SJF non-preemptive vs SRTF (preemptive) — SRTF optimal for min avg WT. SJF is a special case of Priority Scheduling where priority = predicted burst time (inverse).

Priority Scheduling & Round Robin MED

Priority: internal factors (time limits, memory, open files, I/O:CPU ratio) vs external (importance, funds, department). Starvation → fixed by aging. RR: quantum tuning (80% of bursts should finish within q), max wait bound = (n−1)×q — patched, was missing.

Module 4 — Synchronization & Deadlock
Critical Section — 3 Requirements HIGH

Mutual Exclusion, Progress, Bounded Waiting. Disabling interrupts (single-processor only, patched — was missing) is the simplest hardware CS solution but doesn't scale to multiprocessors.

TAS & CAS HIGH

TAS always writes true unconditionally. CAS only writes if current value matches expected — enables lock-free structures. Both are hardware-atomic. Sp26 (most recent PYQ) tested CAS-based reasoning specifically, not raw semaphore code — a likely direction for tomorrow.

Semaphores — wait()/signal(), Low-Level Implementation HIGH

Binary (0/1, mutex-equivalent) vs counting (pool of N resources). Non-busy-wait implementation uses a waiting list + block()/wakeup() — patched, was missing. Starvation can occur if the waiting list is serviced LIFO instead of FIFO (patched, quotable slide fact).

Classical Problems — Bounded Buffer, Readers-Writers, Dining Philosophers HIGH

Bounded Buffer: wait(empty)/wait(full) BEFORE wait(mutex) — reversing causes deadlock. The "lost wakeup" motivating example (patched, was missing) is why semaphores replace naive sleep()/wakeup(). Readers-Writers: read_count logic, first-reader locks writers out. Dining Philosophers: naive solution deadlocks (all pick up left simultaneously); fixes = N−1 seats, asymmetric ordering, or all-or-nothing acquisition.

Slides name semaphores mutex/countFull/countEmpty; textbook-style notes use mutex/full/empty — same logic, different names.
Deadlock — 4 Conditions MED

Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait — all 4 must hold simultaneously. RAG (cycle + single-instance = guaranteed deadlock) is textbook-only, not slide-covered, and had zero appearances across 13 past midterm sittings — know it well enough not to lose an easy mark, but it's the lowest-priority item in this module.

❓Short Questions▼

Tap a question to reveal the answer. Try to recall first.

What's the difference between a zombie and an orphan process?HIGH
Zombie: child has terminated but the parent hasn't called wait() yet, so the PCB/process-table entry lingers. Orphan: parent terminated before the child did; the child is re-parented to init, which periodically calls wait() to clean up its zombies.
Why does disabling interrupts work as a CS solution on a single processor but not on a multiprocessor?HIGH
Disabling interrupts prevents a context switch on that one core, so no other process can run there during the CS. On a multiprocessor, other cores keep running and can still enter their own CS on the same shared data — disabling interrupts only affects the local core.
Why must wait(empty) happen before wait(mutex) in the Bounded Buffer producer?HIGH
If mutex is acquired first and the buffer turns out to be full, the producer would block while holding mutex — permanently locking the consumer out of the buffer it needs to free a slot. Deadlock. Checking empty first ensures the producer only takes mutex when it can actually make progress.
What does Compare-and-Swap (CAS) do that Test-and-Set (TAS) cannot?HIGH
TAS unconditionally writes true regardless of the prior value. CAS only writes the new value if the current value matches an expected value — this conditional check enables lock-free data structures (atomic counters, lock-free queues) where multiple threads can retry without ever blocking.
Why does a very small Round Robin quantum hurt performance?MED
Context switch overhead is pure waste — no useful work happens during a switch. A tiny quantum means the CPU spends more time switching between processes than executing them, degenerating throughput even though responsiveness looks high.
What's the difference between the many-to-one and one-to-one threading models?MED
Many-to-one maps many user threads to a single kernel thread — fast to create, but one blocking syscall stalls the whole process and no true parallelism is possible. One-to-one (Linux/Windows default) maps each user thread to its own kernel thread — true parallelism, no full-process blocking, but higher creation overhead.
What's the difference between concurrency and parallelism?MED
Concurrency means multiple tasks are making progress, possibly by interleaving on a single core — no multi-core requirement. Parallelism means tasks run at the literal same instant, which requires multiple cores.
Why is aging used with priority scheduling?MED
Pure priority scheduling risks starving low-priority processes if high-priority ones keep arriving. Aging gradually increases the priority of a waiting process over time, guaranteeing it eventually becomes highest-priority and runs.
What are the 4 necessary conditions for deadlock?LOW
Mutual Exclusion (resource non-shareable), Hold and Wait (holding one resource while waiting for another), No Preemption (resources only released voluntarily), Circular Wait (a cycle of processes each waiting on the next). All four must hold simultaneously for deadlock.
🧮Analytical Questions▼
Q1fork() trace: predict output and process count for a nested fork() program with printf() callsHIGH▼
1
Draw a tree: root = original process. Each fork() call adds a branch — one node continues as parent (fork returns child PID), one new node is the child (fork returns 0).
2
For N sequential fork() calls with no conditionals, total processes = 2^N (including the original). Track which lines each process actually executes based on its position in the tree — a process only runs code AFTER the fork() call that created it, forward.
3
If wait() is present, check for zombies (child exited, no wait() called before parent also exits) or orphans (parent exits before child, child reparented to init).
4
Count printf() executions by walking the tree — every node that reaches a printf() line in its execution path prints once.
Key insight: Draw the tree first, always. Trying to trace fork() output linearly in your head is the #1 source of errors under exam pressure.
Exam note: appeared in all 13 previous sittings — the single most reliable question on this exam. Recent sittings wrap this in a named scenario (client-server, rover, app) — the underlying fork() logic is unchanged.
Q2MLFQ Gantt chart: given a process table and queue/quantum setup, compute the schedule and TAT/WT/RTHIGH▼
1
Identify the queue structure the question specifies (number of queues, quantum per queue, and — critically — whether the bottom queue is FCFS or Round Robin; don't assume, read the question).
2
New processes enter the top queue. Run each at that level's quantum. If it finishes within quantum, done. If it uses the full quantum, demote one level.
3
Check the promotion rule specified: OSTEP-style periodic boost after time S (all processes reset to top queue), OR the slide's per-I/O-operation promotion (one level up each time a process does I/O). These give different schedules — use whichever the question implies.
4
Build the Gantt chart step by step, tracking each process's remaining burst and current queue level at every scheduling decision point.
5
Compute CT for each process from the chart, then TAT = CT−AT, WT = TAT−BT, RT = first-CPU-time−AT.
Key insight: MLFQ questions fail most often from queue-rule ambiguity, not arithmetic. Nail down which promotion/demotion rule applies before drawing anything.
Exam note: every sitting since Spring 2025 (4/4) has used MLFQ specifically, not plain RR/SRTF/Priority — this is a real difficulty escalation from earlier years' PYQs.
Q3Semaphore scenario: map a real-world description (parking lot / restaurant / bank vault) onto counting semaphore / mutex mechanicsHIGH▼
1
Identify the resource pool size (N spots/tables/slots) → this is the initial value of a counting semaphore.
2
Identify what needs mutual exclusion (e.g. updating a shared counter of available spots) → this needs a separate binary mutex protecting that specific variable.
3
Write wait() at the point where a process wants to acquire a resource; signal() where it releases one.
4
If asked to "find the bug": check for wrong wait/signal ordering (causing deadlock), a missing wait/signal (causing race condition or resource leak), or a semaphore that should be counting but is written as binary (or vice versa).
Key insight: the recent PYQ era (2024 onward) never asks for the 3 classical problems by name — it wraps the identical mechanics in a scenario. Recognize the underlying pattern regardless of the story.
Q4Resource Allocation Graph: given process/resource assignment and request edges, determine if deadlock existsLOW▼
1
Draw all assignment edges (R→P, resource currently held by process) and request edges (P→R, process wants that resource).
2
Trace for a cycle. No cycle = no deadlock, guaranteed.
3
If a cycle exists: check whether every resource type in the cycle has exactly one instance. If yes, deadlock is guaranteed. If any resource type in the cycle has multiple instances, deadlock is only possible, not certain — another process might still release a needed instance.
Exam note: zero appearances across all 13 previous midterm sittings reviewed, and not present in the slide deck (textbook-only). Know the rule well enough for an easy mark if it does appear, but it's the lowest-priority analytical type on this exam.
∑Mathematics▼
Turnaround / Waiting / Response Time
TAT = CT − AT WT = TAT − BT RT = First CPU time − AT
CT = completion time, AT = arrival time, BT = burst time
Round Robin Max Wait Bound
Max wait ≤ (n − 1) × q
n = number of processes, q = time quantum. Slide-confirmed, quick sanity check for RR questions.
SJF Burst Time Estimation (Exponential Average)
τ(n+1) = α·t(n) + (1−α)·τ(n)
t(n) = actual n-th burst, τ(n) = previous prediction, α = weight (typically 0.5)
Averages
Avg TAT = Σ TAT / n Avg WT = Σ WT / n
n = number of processes in the batch
💻Code▼
C — Test-and-Set spinlock
boolean test_and_set(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;
}

// usage:
while (test_and_set(&lock)) ;   // spin
// --- CRITICAL SECTION ---
lock = false;                    // release
TAS always writes true regardless of prior value. Returns the OLD value — if it was false, you just acquired the lock (and set it true); if it was true, you spin.
C — Compare-and-Swap spinlock
int compare_and_swap(int *value, int expected, int new_value) {
    int temp = *value;
    if (*value == expected)
        *value = new_value;
    return temp;
}

// usage:
while (compare_and_swap(&lock, 0, 1) != 0) ;  // spin
// --- CRITICAL SECTION ---
lock = 0;                                       // release
Only writes if current value matches "expected" — this conditional write is what enables lock-free structures. Sp26 PYQ tested CAS-based reasoning directly — practice tracing a CAS-guarded increment across two threads.
C — Bounded Buffer (Producer-Consumer) with semaphores
// mutex=1, empty=N, full=0
// PRODUCER:
do {
    produce item;
    wait(empty);
    wait(mutex);
    add item to buffer;
    signal(mutex);
    signal(full);
} while (true);

// CONSUMER:
do {
    wait(full);
    wait(mutex);
    remove item from buffer;
    signal(mutex);
    signal(empty);
    consume item;
} while (true);
Critical ordering: wait(empty)/wait(full) BEFORE wait(mutex) in both. Reversing causes deadlock — the most common "find the bug" trap on this pattern.
C — Readers-Writers
// WRITER:
wait(rw_mutex);
  [write data]
signal(rw_mutex);

// READER:
wait(mutex);
  read_count++;
  if (read_count == 1) wait(rw_mutex);
signal(mutex);
  [read data]
wait(mutex);
  read_count--;
  if (read_count == 0) signal(rw_mutex);
signal(mutex);
First reader locks out writers (wait(rw_mutex)); last reader unlocks (signal(rw_mutex)). Writers can starve if readers keep arriving — this is the "first readers-writers problem."

🧠Mnemonics & Memory Aids▼
"MHNC" — Deadlock Conditions
Mutual exclusion, Hold and wait, No preemption, Circular wait. All 4 must hold together.
"empty/full before mutex"
In Bounded Buffer, always wait() on the counting semaphore (empty/full) before the binary mutex — protects against deadlocking while holding mutex.
"CAS checks, TAS just takes"
CAS only writes if the current value matches what you expected (conditional) — TAS writes true no matter what (unconditional).
PCB = "PC-SMIA"
Process state, Program Counter, CPU registers, Scheduling info, Memory-mgmt info, I/O status, Accounting info — 6 categories (7 items, Program Counter and CPU registers are often grouped together).
