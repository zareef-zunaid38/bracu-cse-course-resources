## Content

### Slides 3–5: Background and protection
- **Slide 3:** a program must be brought from disk into memory to run; main memory and registers are the only storage the CPU can access directly; the memory unit sees only a stream of addresses plus read (or write) requests; register access takes one CPU clock or less, main memory can take many cycles (a stall); a cache sits between memory and registers; memory protection is required for correct operation.
- **Slides 4–5, base and limit registers:** a pair of base and limit registers defines the logical address space; the CPU checks every user-mode access to be sure it lies between base and limit. Figure: memory 0–1,024,000 with the operating system at the top (from 880,000), three process regions, base = 300,040 and base + limit = 420,940 marked. Hardware check: address ≥ base? and address < base + limit? — if either fails, trap to the OS (illegal addressing error); otherwise access memory.

### Slide 7: Logical vs physical address space
- A logical address space bound to a separate physical address space is central to memory management: a *logical (virtual) address* is generated by the CPU; a *physical address* is what the memory unit sees. They are the same under compile-time and load-time binding and differ under execution-time binding. The logical address space is all logical addresses a program generates; the physical address space is all the physical addresses.

### Slides 9–16: Paging
- **Slide 9:** a process's physical address space can be noncontiguous (allocated whenever memory is available), avoiding external fragmentation and varying-sized chunks. Physical memory is divided into fixed-size *frames* (size a power of 2, between 512 bytes and 16 MB); logical memory into *pages* of the same size; the OS keeps track of free frames; a program of N pages needs N free frames; a page table translates logical to physical addresses; the backing store is split into pages too; internal fragmentation remains.
- **Slide 10, address translation:** the CPU address splits into a *page number* p (index into the page table, which holds each page's base address in physical memory) and a *page offset* d (combined with the base address to form the physical address); for a logical address space of 2ᵐ and page size 2ⁿ, p has m − n bits and d has n bits. **Slide 11:** paging hardware — the CPU's (p, d) looks up frame f in the page table and the physical address is (f, d) in physical memory. **Slide 12:** model with pages 0–3 mapped by a page table (0→1, 1→4, 2→3, 3→7) into frames of physical memory.
- **Slides 13–14, worked example:** n = 2, m = 4, 32-byte memory, 4-byte pages. Logical memory has 16 addresses holding a–p; page table 0→5, 1→6, 2→1, 3→2; physical memory has 32 / 4 = 8 frames (frame 5 holds a b c d, frame 6 holds e f g h, frame 1 holds i j k l, frame 2 holds m n o p). m fixes the number of logical addresses (2ᵐ = 16) and n the offset within a page. Formula: frame number × frame size + offset. The slide asks to map logical address 0 (page 0, offset 0) and logical address 3 (page 0, offset 3); applying the formula gives physical addresses 5 × 4 + 0 = 20 and 5 × 4 + 3 = 23 (computed here; the slide states no answers).
- **Slide 15, internal fragmentation:** page size 2,048 bytes, process size 72,766 bytes = 35 pages + 1,086 bytes, so the last frame wastes 2,048 − 1,086 = 962 bytes; worst case is one frame minus 1 byte; average is half a frame. Small frames seem desirable, but each page-table entry takes memory; page sizes have grown (Solaris supports 8 KB and 4 MB). The process view and physical memory are now very different, and a process can access only its own memory.
- **Slide 16, free frames:** before allocation the free-frame list is 14, 13, 18, 20, 15; a new process with pages 0–3 gets frames 14, 13, 18, 20 (page table 0→14, 1→13, 2→18, 3→20); after allocation the free-frame list is 15.

### Slides 18–23: Page-table implementation
- **Slide 18:** the page table is kept in main memory; the page-table base register (PTBR) points to it and the page-table length register (PTLR) gives its size; every data or instruction access then needs two memory accesses (page table, then data), which is solved with a fast associative cache, the translation look-aside buffer (TLB).
- **Slides 19–20:** associative memory searches in parallel (table of page # → frame #); translation of (p, d): if p is in the associative registers take the frame number from there (TLB hit), otherwise get it from the page table in memory (TLB miss). Figure: paging hardware with a TLB beside the page table.
- **Slide 21, effective access time (EAT):** associative lookup takes ε time units (can be under 10% of a memory access); hit ratio α is the percentage of times the page number is found in the associative registers. With α = 80%, ε = 20 ns and memory access 100 ns: EAT = 0.80 × 120 + 0.20 × 220 = 140 ns. With a more realistic α = 99%: EAT = 0.99 × 120 + 0.01 × 220 = 121 ns.
- **Slide 22, memory protection:** a protection bit per frame says whether access is read-only or read-write (more bits can mark execute-only, etc.); a valid–invalid bit on each page-table entry marks whether the page is in the process's logical address space ("valid" = legal page, "invalid" = not in it), or the PTLR can be used; violations trap to the kernel. **Slide 23 figure:** pages 0–5 with page-table entries 0→frame 2 (v), 1→3 (v), 2→4 (v), 3→7 (v), 4→8 (v), 5→9 (v), 6→0 (i), 7→0 (i).

### Slides 25–26: Shared pages
- Shared code: one copy of read-only (reentrant) code shared among processes (text editors, compilers, window systems), like threads sharing a process space, and useful for IPC if read-write sharing is allowed; private code and data: each process keeps its own copy, and those pages can appear anywhere in the logical address space. Figure: three processes each with `libc 1`–`libc 4` whose page tables all point at the same frames (3, 4, 6, 1), so physical memory holds one copy of each libc page.

### Slides 28–30: Structure of the page table
- **Slide 28:** straightforward paging structures get huge: a 32-bit logical address space with 4 KB pages (2¹²) has 2³² / 2¹² = 1 million entries; at 4 bytes each that is 4 MB of page table alone, which we do not want to allocate contiguously.
- **Slide 29, hierarchical page tables:** break the logical address space into multiple page tables — a simple technique is a two-level page table (page the page table); figure: outer page table → pages of the page table → memory.
- **Slide 30, two-level example:** 32-bit machine, 1 KB page size: a 22-bit page number and 10-bit page offset; since the page table is itself paged, the page number splits into a 12-bit p₁ and a 10-bit p₂, giving the layout p₁ (12) | p₂ (10) | d (10), where p₁ indexes the outer page table and p₂ is the displacement within the inner page-table page. Known as a forward-mapped page table.

### Slides 32–36: Virtual memory and demand paging
- **Slide 32:** "virtual memory" appears to be present but actually is not; it lets a program use more memory than the machine has, and is used when processes exceed main memory; when the computer runs out of physical memory it writes its needs to a swap file on the hard disk as "virtual memory".
- **Slide 33, demand paging:** bring a page into memory only when needed — less I/O, less memory, faster response, more users; disadvantage: page-fault interrupts; needs hardware support: a page table with a valid–invalid bit, and secondary memory. Figure: main memory holding pages of programs A and B with swap out / swap in against disk.
- **Slide 34, valid–invalid bit:** an extra page-table bit says whether the page is in main memory; if valid, continue normally; if invalid, a page-fault trap occurs. Page needed ⇒ reference to it; invalid reference ⇒ abort; not in memory ⇒ bring it in. Figure: logical pages A–H, a page table with frames and valid bits, physical memory, and the backing store.
- **Slide 35, page fault:** the first reference to a page traps to the OS; the OS checks another table — invalid reference ⇒ abort, otherwise just not in memory; find a free frame; load the page from disk into it; reset the tables (validation bit = 1); restart the instruction that faulted. Figure steps: 1 reference, 2 trap, 3 page is on the backing store, 4 bring in the missing page, 5 reset the page table, 6 restart the instruction.
- **Slide 36, flowchart:** start an instruction → generate address → page number → is the page in main memory? yes → fetch data and complete the instruction; no → page-fault interrupt → is there a free frame? yes → get the disk address of the new page → read the page in → adjust the page table → restart the interrupted instruction; no → select a page for replacement → was the page modified? yes → write it back to disk → adjust the page table → continue.

### Slides 37–40: Page replacement
- **Slide 37:** algorithms FIFO, LRU and OPT. Figure of the basic scheme: 1 swap out the victim page, 2 change its entry to invalid, 3 swap the desired page in, 4 reset the page table for the new page.
- **Slides 38–40, one example for all three:** reference string (times 1–12) P2, P3, P2, P1, P5, P2, P4, P5, P3, P2, P5, P2 with 3 frames; the slides draw the frame contents at each step and mark hits.
  - **FIFO** (replace the page that has been in memory longest): hits at t = 3, 8, 10 → 3 hits, 9 page faults.
  - **LRU** (replace the least recently used page; can be implemented with a counter per page): hits at t = 3, 6, 8, 11, 12 → 5 hits, 7 page faults.
  - **Optimal** (replace the page not to be used for the longest time in the future): hits at t = 3, 6, 8, 9, 11, 12 → 6 hits, 6 page faults.
  (Hit marks read from the slides; the totals were also checked by simulating the three algorithms on this reference string.)
