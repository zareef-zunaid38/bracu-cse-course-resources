## Topic 24 — Memory Basics: Address Spaces, Binding, Logical vs Physical
**Ref: Silberschatz 9.1.1, 9.1.3**

### Address Binding
A program goes through stages before execution, and its addresses can be bound to physical memory at different points:

| Binding time | When | Notes |
|---|---|---|
| **Compile time** | If memory location is known in advance | Generates absolute code. Must recompile if starting address changes. Rare today. |
| **Load time** | If location not known at compile time | Generates relocatable code. Binding happens when the program is loaded. |
| **Execution time** | If the process can be moved during execution | Binding delayed until run time. Requires hardware support (base/limit or relocation registers). Most modern systems use this. |

### Logical vs Physical Address Space
- **Logical (virtual) address:** generated by the CPU — what the running program sees.
- **Physical address:** the actual address seen by the memory unit — what's loaded into the memory-address register.
- Compile-time and load-time binding: logical address = physical address (no translation).
- Execution-time binding: logical and physical addresses **differ** — this distinction is the basis of virtual memory.

### MMU (Memory Management Unit)
Hardware device that maps logical → physical addresses at run time.

**Simple relocation-register scheme:**
```
Physical address = Logical address + Relocation register value
```
The user program only ever deals with logical addresses (0 to max) — it never sees the real physical address. Mapping is invisible to the process.

### Base and Limit Registers (Hardware Address Protection)
A pair of registers defines the bounds of a process's logical address space:
- **Base register:** the smallest legal physical address.
- **Limit register:** the size of the range (or, in some framings, the largest legal address).

```
CPU (in user mode) checks every memory access:
   base ≤ address < base + limit   → allowed
   otherwise                        → trap to the OS (addressing error)
```
This is the hardware mechanism that actually *enforces* memory protection between processes — each process only ever sees addresses that pass this check, and the OS updates base/limit on every context switch.

### Dynamic Loading and Dynamic Linking
- **Dynamic loading:** a routine is not loaded until it's actually called. Better memory-space utilization — unused routines are never loaded. Does not require special OS support, just program structure.
- **Static linking:** system libraries combined into the binary at compile time.
- **Dynamic linking:** linking postponed until execution time. Small stub locates the in-memory library routine (or loads it). Saves space — one shared library copy serves all processes using it (e.g., `.so` / `.dll` files).

## Topic 25 — Contiguous Allocation and Fragmentation
**Ref: Silberschatz 9.3**

> **Slide-verification note:** the theory slide deck (`module06_memory_management.pptx`) has **no section on contiguous allocation at all** — it jumps directly from address-space background (base/limit registers) to paging, skipping first-fit/best-fit/worst-fit and external/internal fragmentation as a topic entirely. This entire topic is Silberschatz-textbook-only, same status as Peterson's Solution in Module 4. It's still in the confirmed Topic 20–32 Final syllabus range per the topic map, so keep it — but if slide-based questions dominate the exam, this is lower-probability material than the rest of the module. Internal fragmentation itself *does* reappear briefly under Paging below, just not the contiguous-allocation framing of it.

### Contiguous Memory Allocation
Each process is allocated a single contiguous block of memory.

**Fixed-size partitions:** memory divided into fixed regions at boot. Simple, but wastes memory if a process is smaller than its partition (internal fragmentation), and caps max process size at partition size.

**Variable-size partitions:** OS tracks a table of allocated/free blocks (holes). Free holes of various sizes scattered through memory. As processes arrive, allocated from a suitably large hole; as they exit, memory is returned and merged with adjacent free holes.

### Dynamic Storage-Allocation Algorithms
Given a set of holes, which one to allocate to a new process?

| Algorithm | Strategy | Trade-off |
|---|---|---|
| **First-fit** | Allocate the *first* hole big enough | Fast |
| **Best-fit** | Allocate the *smallest* hole big enough | Minimizes leftover waste per allocation, but leaves many tiny unusable holes over time; must search entire list unless sorted |
| **Worst-fit** | Allocate the *largest* hole | Leaves the largest possible leftover hole, which is more likely to be reusable — but simulations show it performs worst overall |

> **Exam note:** First-fit and best-fit are generally shown to be better than worst-fit in both time and storage utilization. First-fit is typically faster.

### Fragmentation

| Type | Cause | Fix |
|---|---|---|
| **External fragmentation** | Enough *total* free memory exists, but it's scattered in pieces too small individually to satisfy a request | **Compaction** — shuffle memory contents to consolidate free space into one block. Only possible if relocation is dynamic (execution-time binding). |
| **Internal fragmentation** | Allocated memory block is slightly larger than requested (e.g., allocation rounded up to a fixed block size) — the leftover *inside* the allocated block is wasted | Inherent trade-off of fixed-size allocation units; reduced but not eliminated by paging (below) |

> **50-percent rule:** given random allocation/deallocation patterns, statistical analysis shows roughly **1/3 of memory can become unusable** to external fragmentation (for N allocated blocks, expect ~0.5N additional blocks lost to fragmentation) — this is the classic argument for why contiguous allocation alone doesn't scale, motivating paging.

## Topic 26 — Paging: Page Table, Frames, Address Translation
**Ref: Silberschatz 9.4.1**

### Paging — Basic Method
Paging **eliminates external fragmentation entirely** by avoiding contiguous allocation altogether.
- Physical memory divided into fixed-size blocks: **frames**.
- Logical memory divided into same-size blocks: **pages**.
- To run a program of N pages, find N free frames anywhere in physical memory — they need not be contiguous.
- A **page table** per process maps page number → frame number.

### Address Translation

A logical address of size L bits, with page size 2^d, splits into:

```
Logical Address = [ Page Number (p) | Page Offset (d) ]
                     (L − d bits)         (d bits)
```

- **Page number (p):** index into the page table → gives the frame number.
- **Page offset (d):** combined unchanged with the frame number to form the physical address (the offset within the frame is identical to the offset within the page — only the frame number differs from the page number).

```
Physical Address = [ Frame Number (from page table[p]) | Page Offset (d) ]
```

**Worked example (decimal method)** — page size = 4 KB (2¹² → offset = 12 bits), logical address = 15,367 (decimal):
```
Page number   p = 15367 / 4096 = 3   (integer division)
Page offset   d = 15367 % 4096 = 3079

Look up page table[3] → suppose it returns frame 6.
Physical address = (6 × 4096) + 3079 = 24576 + 3079 = 27655
```

> **Key skill:** Given a logical address, page size, and a page table (array mapping page → frame), compute page number and offset by division/modulo against the page size, look up the frame, then reassemble the physical address. This is the standard exam calculation.

**Slide/practice-sheet notation:** for a logical address space of 2^m and page size 2^n, `m` is the total number of address bits and `n` is the offset width — `p = m − n` bits for the page number. The practice sheet gives logical addresses as **binary strings** (fixed bit-width) rather than decimal numbers, so the split is done by cutting the bit string, not by division:

**Worked example (binary method)** — matches the practice sheet's own style: 5-bit logical address space (m=5), page size 2 bytes (n=1 bit offset) → page number = 4 bits, offset = 1 bit.
```
Logical address 01001 (binary)
   split: page number = 0100 (=4), offset = 1
   → look up page table[4] for process → frame f
   → physical address = f (in the page-table units given) with offset 1 appended/added
```
Both methods are the same math — decimal div/mod vs binary bit-cutting — pick whichever the question's input format matches. When addresses are given as binary strings, cut the bits directly rather than converting to decimal first, since page tables in these problems are usually indexed by the raw page-number bits.

### Internal Fragmentation — Worked Calculation
Paging still wastes space when a process's last page isn't fully used.
```
internal_fragmentation = page_size − (process_size mod page_size)     [when the remainder is nonzero]
```
**Worked example** — page size = 2,048 bytes, process size = 72,766 bytes:
```
72,766 / 2,048 = 35 pages, remainder 1,086 bytes   (35 full pages + a 36th partial page holding 1,086 B)
Internal fragmentation = 2,048 − 1,086 = 962 bytes
```
- **Worst case:** a process's last page uses only 1 byte → wastes almost a full frame (`frame size − 1`).
- **On average:** expected internal fragmentation ≈ **½ a frame size** per process.
- This creates a real trade-off: smaller pages reduce internal fragmentation, but increase the number of page-table entries needed (more memory spent on the page table itself) — one reason page sizes have grown over time (e.g., Solaris supports both 8 KB and 4 MB pages).

### Shared Pages
Paging enables efficient sharing of code between processes:
- **Shared code:** one read-only (**reentrant**) copy of code shared by multiple processes (e.g., a text editor, compiler, or windowing system opened by several users at once) — similar in spirit to multiple threads sharing one process's address space. If read-write sharing is allowed, this also doubles as an IPC mechanism.
- **Private code and data:** each process keeps its own separate copy; these pages can be placed anywhere in that process's logical address space.

### Page Table Structure Details
- **Valid–invalid bit:** per entry, marks whether that page belongs to the process's logical address space. Accessing an invalid page → trap (segmentation fault).
- **Protection bits:** read/write/execute permissions per page.
- Internal fragmentation still possible: if a process's last page isn't fully used, the unused remainder of that frame is wasted (bounded by page size, unlike contiguous allocation's unbounded external fragmentation).

### TLB (Translation Lookaside Buffer)
Every logical memory reference would otherwise need **two** physical memory accesses (one to read the page table, one for the actual data) — the TLB is a small, fast associative-memory cache of recent page-table entries to avoid this.

**Effective Access Time (EAT) with TLB:**
```
EAT = hit_ratio × (TLB access time + memory access time)
    + miss_ratio × (TLB access time + memory access time + memory access time)
```
(A TLB miss costs an extra page-table lookup in memory before the actual data access.)

**Worked example** — TLB access = 20 ns, memory access = 100 ns, hit ratio = 80%:
```
EAT = 0.8 × (20 + 100) + 0.2 × (20 + 100 + 100)
    = 0.8 × 120 + 0.2 × 220
    = 96 + 44
    = 140 ns
```

> **Key skill:** This EAT calculation is a standard exam question — memorize the formula structure (hit case = 1 memory access, miss case = 2 memory accesses, both plus TLB access time) rather than the numbers.

### Multilevel (Hierarchical) Paging
For large address spaces, a single-level page table itself becomes too large to fit contiguously in memory. Solution: page the page table itself.

**Two-level paging** splits the page number further:
```
Logical Address = [ Outer Page Number (p1) | Inner Page Number (p2) | Offset (d) ]
```
`p1` indexes an outer page table, whose entries point to inner page tables; `p2` indexes the inner table to get the actual frame number. Extra levels trade page-table memory usage for extra memory accesses per translation (mitigated in practice by the TLB).

**Textbook's own worked example (32-bit machine, 1 KB pages):** total page number = 22 bits (2³²/2¹⁰), offset = 10 bits. That 22-bit page number is itself paged: split into a 12-bit outer page number (p1) and a 10-bit inner page number (p2). This is the standard "forward-mapped page table" example Silberschatz uses — recognize it, but see below for how to *derive* a split rather than just recite this one.

### Key Skill (3) — Deriving How Many Levels Are Needed
This is the actual practice-sheet skill (Problems 4, 6, 7 are all this): given total address bits, page size, and page-table-entry size, derive the number of levels and each level's bit-width so that **every level's table fits in exactly one frame**.

```
1. offset bits (n)        = log2(page size)
2. page-number bits (P)    = total address bits − n
3. max bits per table (k)  = log2(frame size / entry size)     [frame size = page size, normally]
4. number of levels        = ceil(P / k)
5. split P into chunks of k bits each, working from the OFFSET outward (innermost level = k bits,
   next level out = k bits, ... ; the outermost/last level takes whatever remains, ≤ k bits)
6. Translation: index the outermost table with its bit-chunk → get a pointer to the next table →
   index that with the next chunk → ... → innermost table entry gives the frame number →
   combine with the original offset (d) for the physical address.
```

**Worked example — matches practice-sheet Problem 6's exact numbers:** 8-bit logical address space, page size = 16 B, page-table entry size = 4 B, main memory = 512 B.
```
n = log2(16) = 4 bits (offset)
P = 8 − 4 = 4 bits (page number)
k = log2(16 / 4) = log2(4) = 2 bits per table level

Levels needed = ceil(4 / 2) = 2   → two-level paging suffices

Split: outer page number (p1) = 2 bits, inner page number (p2) = 2 bits, offset (d) = 4 bits
Logical address = [ p1 (2 bits) | p2 (2 bits) | d (4 bits) ]  = 8 bits total ✓

Each table has 2² = 4 entries × 4 B/entry = 16 B = exactly 1 frame ✓ (confirms the split is correct)
```
To translate an address: convert to binary, cut into `p1 | p2 | d`, look up `p1` in the outer table to find the frame holding the correct inner table, look up `p2` in that inner table to get the final frame number, then append `d` unchanged.

> **Exam note:** If step 4 gives more than 2 levels (as in a larger address space), keep chunking — the outermost level absorbs whatever bits are left over even if that's less than a full `k` bits (it doesn't need to fill an entire frame, just fit within one). Problems with 3+ levels ("3rd outer PMT", "2nd outer PMT", etc.) use exactly this same repeated-chunking method — just more of it.

## Topic 27 — Virtual Memory and Demand Paging
**Ref: Silberschatz 10.1, 10.2.1, 10.2.2**

### Virtual Memory
Separates a process's logical memory (as the program sees it) from physical memory (what's actually loaded). Allows a program **larger than physical memory** to run, and increases multiprogramming by loading only what's needed.

### Demand Paging
Pages are loaded **only when referenced** (lazy loading), not all at once at process start.

**Valid–invalid bit reused for demand paging:**
- **Valid:** page is both legal and currently in physical memory.
- **Invalid:** either the page is not part of the logical address space, **or** it's a legal page that simply isn't in memory yet.

### Page Fault Handling — Sequence
```
1. CPU references a page marked invalid in the page table.
2. Trap to the OS (page fault).
3. OS checks an internal table: is this reference valid (just not-yet-loaded) or truly illegal?
     - Illegal → abort the process.
     - Valid → continue.
4. Find a free frame (from the free-frame list, or evict a page — see Topic 28).
5. Schedule a disk operation to read the desired page into the newly allocated frame.
6. Once the read completes, update the process's page table: mark the page valid, record the frame.
7. Restart the instruction that caused the page fault (the CPU re-fetches it from scratch).
```

> **Exam note:** Step 7 matters — the trapping instruction is restarted from the beginning, not resumed mid-instruction, since the hardware state at the trap point is generally not preserved precisely enough to resume partway.

### Effective Access Time with Page Faults
```
EAT = (1 − p) × memory_access_time + p × page_fault_service_time
```
where `p` = probability of a page fault (0 ≤ p ≤ 1). Because `page_fault_service_time` is dominated by disk I/O (on the order of milliseconds, ~10⁵–10⁶ times slower than a memory access in nanoseconds), even a **small page-fault rate causes severe slowdown** — this is the standard exam takeaway.

**Worked example** — memory access = 100 ns, page fault service time = 8 ms = 8,000,000 ns, p = 0.001:
```
EAT = 0.999 × 100 + 0.001 × 8,000,000
    = 99.9 + 8,000
    ≈ 8,099.9 ns  (≈ 81× slower than pure memory access)
```

## Topic 28 — Page Replacement Algorithms: FIFO, Optimal, LRU
**Ref: Silberschatz 10.4.2–10.4.4**

When a page fault occurs and **no free frame** is available, an existing page must be evicted (replaced) to make room. Which page to evict is the page-replacement problem — the choice of algorithm directly affects page-fault frequency.

### FIFO (First-In-First-Out)
Evict the page that has been in memory the **longest**, regardless of how recently it was used. Simple to implement (a queue), but performance is often poor — and suffers **Belady's Anomaly**: increasing the number of frames can, counter-intuitively, *increase* the number of page faults for some reference strings.

### Optimal (OPT / MIN)
Evict the page that will **not be used for the longest time in the future**. Guarantees the lowest possible page-fault rate for any reference string. **Not implementable in practice** (requires future knowledge) — used only as a theoretical benchmark to measure how close a real algorithm gets.

### LRU (Least Recently Used)
Evict the page that has **not been used for the longest time in the past** — an approximation of Optimal that only looks backward, which is actually knowable. Does not suffer Belady's Anomaly. Requires hardware support (counters or a stack) to track recency efficiently.

### Worked Example — Standard Reference String, 3 Frames
**Reference string:** `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1`

**FIFO trace** (evict oldest-loaded page):

| Ref | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 | 1 | 2 | 0 | 1 | 7 | 0 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Frame 1 | 7 | 7 | 7 | 2 | 2 | 2 | 0 | 0 | 0 | 3 | 3 | 3 | 3 | 1 | 1 | 1 | 1 | 7 | 7 | 7 |
| Frame 2 | | 0 | 0 | 0 | 0 | 3 | 3 | 3 | 2 | 2 | 0 | 0 | 0 | 0 | 2 | 2 | 2 | 2 | 0 | 0 |
| Frame 3 | | | 1 | 1 | 1 | 1 | 1 | 4 | 4 | 4 | 4 | 4 | 2 | 2 | 2 | 0 | 0 | 0 | 0 | 1 |
| Fault? | ● | ● | ● | ● | | ● | ● | ● | ● | ● | ● | | | ● | ● | | | ● | ● | ● |

**FIFO total: 15 page faults**

**LRU trace** (evict least-recently-used):

| Ref | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 | 1 | 2 | 0 | 1 | 7 | 0 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Fault? | ● | ● | ● | ● | | ● | | ● | ● | ● | ● | | | ● | | ● | | ● | | |

**LRU total: 12 page faults**

**Optimal trace** (evict page used furthest in the future, or never again):

| Ref | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 | 1 | 2 | 0 | 1 | 7 | 0 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Fault? | ● | ● | ● | ● | | ● | | ● | | | ● | | | ● | | | | ● | | |

**Optimal total: 9 page faults**

| Algorithm | Faults | Relative performance |
|---|---|---|
| FIFO | 15 | Worst — no recency awareness |
| LRU | 12 | Close to Optimal, no future knowledge needed |
| Optimal | 9 | Theoretical best — unimplementable benchmark |

> **Key skill:** Be able to reproduce a trace like this for any given reference string and frame count. Method: for FIFO, track load order and evict the earliest-loaded page still resident. For LRU, track most-recent-use order and evict the page unused longest so far. For Optimal, at each fault, scan forward in the reference string for each resident page and evict whichever is used furthest away (or never again).

> **Practice-sheet framing — hit ratio / fault ratio, not raw counts:** the actual practice sheet (Problem 8) asks for **hit ratio** and **fault ratio** as percentages, not the raw fault count used above. Convert directly:
> ```
> fault ratio = (number of faults / total references) × 100%
> hit ratio   = 100% − fault ratio
> ```
> e.g. for a 16-reference string with 4 frames, practice-sheet Problem 8 gives: FIFO → 68.75% fault / 31.25% hit; LRU → 62.5% fault / 37.5% hit; Optimal → 56.25% fault / 43.75% hit. Same trace method as above, just report the result as a percentage.
